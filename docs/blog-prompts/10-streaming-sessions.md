# 10. 4-3 실시간 세션화: 세션 윈도, 키별 상태, 경계 규칙, 늦은 이벤트가 세션을 잇는 일

- 대상 코드: `pipeline/stream_sessions.py`, `tests/test_stream_sessions.py`, `bench/stream_once.sh`의 `JOB=sessions`
- 설계 기록: [ADR 0009](../decisions/0009-stage4-streaming.md) 결정 7, '4-3 결과' 절. 3단계 세션 규칙은 [ADR 0007](../decisions/0007-stage3-modeling.md) 결정 2
- 상태: 미답변

## 다룬 개념
- **세션 윈도**: 길이가 정해진 윈도가 아니다. 활동 사이의 간격(30분)으로 나뉘고, 키(사용자)마다 따로 열리고 닫힌다.
- **키별 상태**: 열린 세션마다 상태가 필요하다. 그래서 상태 크기는 동시에 활동하는 키 수에 비례한다.
- **늦은 이벤트와 세션 병합**: 워터마크 안에서 늦게 온 이벤트는 따로 있던 두 세션을 하나로 이을 수 있다. 이벤트 시간으로 세면 도착 순서와 상관없이 같은 결과가 나온다.
- **경계 규칙 맞추기**: 배치와 실시간이 같은 규칙(1,800초까지 같은 세션)을 쓰는지 테스트로 고정한다. 문서만으로는 경계를 알 수 없었다.
- **세션이 닫히는 시점**: 워터마크가 '마지막 이벤트 + 간격'을 지나야 세션이 나온다. 입력이 끊기면 마지막 세션들이 갇힌다.

## 질문 (답은 블로그에)
1. 같은 입력에서 1분 퍼널의 상태는 최대 16행이었고, 세션은 최대 44,215행(36.1MiB)이었다.
   - 왜 이렇게 다른가?
   - 하루 전체(사용자 수백만)를 실시간으로 세션화한다면 무엇을 걱정해야 하나? 메모리, JVM 쓰레기 수집, 체크포인트 크기를 떠올려라.
2. 이벤트의 5%가 최대 8분 늦게 뒤섞여 들어왔는데, 실시간 세션 103,053개가 배치와 시작·끝·이벤트 수까지 모두 같았다.
   - 어떻게 가능한가?
   - 테스트에서 늦게 온 10:20 이벤트가 10:00 세션과 10:40 세션을 하나로 이은 과정을 상태 기준으로 설명하라.
   - 그 이벤트가 워터마크보다 늦게 왔다면 결과는 어떻게 달라지나?
3. (면접형) 처음에 간격을 1,801초로 줬다가, 1,801초 떨어진 이벤트까지 한 세션으로 묶였다.
   - Spark 세션 윈도의 경계는 포함인가, 제외인가?
   - 공식 문서("latest input of the session + gap duration")만으로는 왜 알 수 없었나?
   - 배치와 실시간의 규칙을 어떻게 일치시켰고, 무엇으로 고정했나?
4. 세션 실험에서는 틱을 45분 뒤로 보냈다. 1분 퍼널에서는 30분이었다.
   - 왜 더 길어야 하나?
   - 실제 서비스에는 재생기의 틱이 없다. 새벽에 트래픽이 끊기면 마지막 세션들은 언제 나오나? 이 '입력이 멈춘 소스' 문제를 어떻게 풀겠나?
5. (면접형) 3단계 배치 세션은 UTC 자정에서 끊었다. 실시간 세션 윈도에는 자정 절단이 없다.
   - 하루 전체를 실시간으로 돌리면 두 결과는 어디서 달라지나?
   - 대시보드 숫자를 배치와 맞춰야 한다면 어느 쪽을 어떻게 바꾸겠나?

## 직접 돌려 볼 실험
1. **워터마크보다 늦은 이벤트가 세션 개수를 바꾸는지 보기** (`docker compose --profile stream up -d kafka` 뒤)
   ```bash
   JOB=sessions bench/stream_once.sh events_s2 -- --tick-minutes 45
   ```
   볼 것: 이번에는 워터마크보다 늦은 이벤트(0.5%)가 섞인다. 대조가 실패할 수 있다. 배치와 실시간의 세션 수와 이벤트 수가 각각 어느 방향으로 다른지 보고 이유를 적어라. 이벤트가 하나 빠지면 세션이 갈라지기도 한다.
2. **틱이 짧으면 무엇이 갇히나**
   ```bash
   JOB=sessions bench/stream_once.sh events_s3 -- --very-late 0 --tick-minutes 30
   ```
   볼 것: 실시간 세션이 배치보다 적을 것이다. 빠진 세션들의 `session_end`가 재생 구간의 끝 몇 분에 몰려 있는지 확인한다. 틱 30분에서 워터마크 10분을 빼면 20분인데, 세션 간격 30분보다 짧다는 것과 연결해 설명하라.

## 학습 자료
링크는 2026-10-12에 열리는 것을 확인했다.
- [Spark 4.1.2 — Structured Streaming(데이터프레임 API)](https://spark.apache.org/docs/4.1.2/streaming/apis-on-dataframes-and-datasets.html): 'Types of time windows' 절만 본다.
  > 요약: 시간 윈도는 텀블링(고정), 슬라이딩, 세션 세 가지다. 세션 윈도는 마지막 입력 뒤 간격 동안 입력이 없으면 닫힌다. 간격은 고정값 대신 행마다 다른 식(예: 사용자 등급별 간격)으로 줄 수도 있다.
- [PySpark 4.1.2 — pyspark.sql.functions.session_window](https://spark.apache.org/docs/4.1.2/api/python/reference/pyspark.sql/api/pyspark.sql.functions.session_window.html)
  > 요약: 세션의 끝은 '그 세션의 마지막 입력 시각 + 간격'이라, 새 입력이 오면 끝이 늘어나는 동적인 윈도다. 결과는 `start`와 `end`를 가진 구조체 컬럼이다. 경계를 포함하는지는 적혀 있지 않다. 이 프로젝트에서는 테스트(`…exactly_1800s_stays_in_session…`)로 확인했다.

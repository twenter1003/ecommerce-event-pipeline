# 이력서·면접용 문장 초안

README와 ADR의 실측값만 썼다. 문장 끝의 괄호는 근거 ADR이다. 지원하는 회사에 맞춰 순서와 강조를 바꿔 쓴다.

**쓰는 기준:** 설계·코드·테스트는 AI 코딩 에이전트(Claude Code)가 맡았다. 그래서 구현을 내가 했다고 쓰지 않는다. 내가 정한 것과 프로젝트가 해낸 것을 나눠 쓴다(README '만든 방식', 회고 '학습 방식').

## 프로젝트 한 줄
**B2C 이벤트 로그 데이터 파이프라인** (개인 학습 프로젝트, AI 코딩 에이전트 Claude Code와 협업, 2026-10)
실제 이커머스 행동 로그 4.1억 건으로 배치 적재부터 실시간 스트리밍까지 구현하고, 단계마다 결과를 독립 계산과 대조한 프로젝트다. 구현은 Claude Code가, 학습 방향 결정과 비용 승인은 내가 맡았다.
PySpark · Airflow · Iceberg · Kafka · Spark Structured Streaming · Terraform · GCP(Composer, Dataproc)

## 내 역할
- **학습 방향 결정:** Claude가 후보와 트레이드오프를 비교해 올린 안에서 단계 순서(레이크하우스 → GCP 이전 → 실시간)와 기술을 골랐다. 3단계 저장소는 "이 규모에는 필요 없다"는 추천과 달리, MERGE·원자적 커밋·시간 여행을 배우려고 SeaweedFS + Iceberg를 골랐다. (ADR 0001·0006·0009)
- **개발 방식 전환:** 처음 사흘(10/3~10/5)은 핵심 로직을 직접 짜려 했다. 아직 모르는 것을 내가 결정해야 하는 구조에서 막혀, AI가 구현하고 나는 설명하며 배우는 방식으로 바꿨다. 그 뒤 엿새 만에 네 단계를 모두 마쳤다.
- **작업 규칙과 비용 승인:** "결정은 후보 비교와 트레이드오프를 담은 ADR로 남긴다", "실행해서 확인한 것만 완료로 보고한다"는 규칙을 두었다. 클라우드 작업은 추정 비용과 상한을 보고 승인했다(약 ₩1.2만, 결제 기록 대조 전 추정).

## 프로젝트 결과 (이력서에는 5개 중 3~4개)
이력서에 옮길 때는 프로젝트 줄의 "AI 코딩 에이전트 Claude Code와 협업"을 반드시 함께 쓴다. 아래는 내 구현이 아니라 프로젝트의 결과다.
- **멱등 배치 파이프라인:** PySpark와 Airflow로 일 단위 멱등 적재와 품질 검사 8개. 7개월 213일(4.1억 행)을 42분에 백필했고 실패는 0이다. 동시 실행 수(1~4)를 실측해, 메모리 한계로 상한을 3으로 정했다. (ADR 0003·0004·0005)
- **레이크하우스 모델링:** SeaweedFS(S3 호환) 위 Iceberg에 30분 세션화, 상품 이력(SCD2), 퍼널·코호트 마트.
  - SCD2는 원하는 상태를 매번 계산해 차이만 MERGE한다. 다시 돌리면 커밋이 0이다.
  - 코호트 크기(15,639,803)와 카테고리 변경 수(168,736)가 독립 쿼리와 정확히 같았다.
  - (ADR 0006·0007)
- **원천 데이터 결함 발견과 대응:** 원천 결함 다섯 가지를 숫자로 찾아 기록하고 대응했다.
  - 세션 id 정의가 바뀐 날(2020-03-25) → 검증 기준을 고장 감지 방식으로 다시 세웠다.
  - 카테고리가 의미 없이 다시 매겨짐(2019-12-01) → SCD2로 과거 보고서를 지켰다. Type-1이었다면 11월 매출의 61%가 옮겨 갔다.
  - 10월 장바구니 기록 누락 → 달끼리 비교하는 기본 지표를 세션 전환율로 정했다.
  - 이벤트가 평소의 10%인 날(2/27)과 구매가 0~29건인 날 4일 → 품질 검사의 사각지대로 기록했다.
  - (ADR 0007)
- **클라우드 이전(GCP):** Terraform으로 Composer와 Dataproc을 코드화하고, 같은 DAG를 환경 변수 분기만으로 옮겼다.
  - Dataproc 기본 커미터가 동시 쓰기에서 데이터를 조용히 잃는 문제의 원인을 찾아 해결했다. YARN 코어 굶주림도 풀었다.
  - 213일 결과가 로컬과 행 단위로 같았다. 비용은 약 ₩1.2만(추정)이고, 자동 삭제 안전장치를 실제로 실행해 검증했다.
  - (ADR 0008)
- **실시간 처리:** Kafka와 Spark Structured Streaming으로 실시간 1분 퍼널과 세션화.
  - 이벤트 시각을 옮겨 재생하는 도구로 지연과 순서 뒤바뀜을 재현하고, 워터마크(5·10·20분)의 손실·지연·상태 트레이드오프를 실측했다.
  - 강제 종료 후 재시작해도 결과가 배치와 같았다(정확히 한 번).
  - 실시간 세션 103,053개가 배치 세션과 완전히 일치했다.
  - (ADR 0009)

## 면접 2분 소개 (말로 하는 버전)
> 실제 이커머스 로그 4억 건으로 배치 적재부터 실시간 스트리밍까지 이어지는 데이터 파이프라인을 만든 학습 프로젝트입니다. 구현은 AI 코딩 에이전트인 Claude Code가 맡았습니다. 저는 무엇을 어떤 순서로 배울지 정하고, 만들어진 것을 제 말로 설명할 수 있게 공부하는 것을 맡았습니다. 처음 사흘은 직접 짜려다 모르는 결정 앞에서 멈췄고, 그래서 방식을 바꿨습니다.
>
> 이 방식에서 가장 신경 쓴 것은 "AI가 만든 결과가 맞다는 것을 어떻게 아느냐"였습니다. 결정마다 후보 비교를 문서로 남기고, 실행해서 확인한 것만 완료로 보고하게 규칙을 두었습니다. 그래서 단계마다 결과를 파이프라인 밖의 독립 계산과 숫자로 맞춘 뒤에야 완료로 봤습니다. 그 대조에서 성공으로 끝난 클라우드 잡이 데이터를 조용히 잃은 것이 드러났습니다. 원인은 Dataproc의 기본 커미터 설정이었습니다. 실시간에서는 엔진이 보고하는 지표가 이벤트가 아니라 부분 집계된 행을 센다는 것도 드러났습니다. 둘 다 Claude가 원인을 공식 문서와 코드로 확인해 고쳤고, 고친 뒤 다시 숫자로 맞췄습니다.
>
> 추천을 그대로 따르지 않은 결정도 있습니다. 레이크 저장소는 이 규모에는 필요 없다는 추천을 받았지만, MERGE와 원자적 커밋을 배우려고 Iceberg를 골랐습니다.

# 0005. 7개월 성능 측정: 동시 실행 수, 하루씩 vs 한 번에, 처리량, 병목

- 날짜: 2026-10-06
- 단계: 2 (3단계 설계의 근거가 된다)
- 상태: 채택

## 배경
프로젝트를 빨리 끝내야 한다. 그래서 "매일 하루치가 도착하는" 흐름을 더 흉내 내는 대신, 만든 파이프라인이 얼마나 버티고 어디서 막히는지 재기로 했다(2026-10-06 사용자 결정). 하루치 구조(ADR 0003·0004)는 그대로 둔다. 날짜 단위로 다시 처리할 수 있는 것이 이 구조의 핵심이기 때문이다. 나머지 6개월(2019-11~2020-04)을 받아 7개월, 213일치로 잰다.

## 측정 환경
- 장비: 노트북 Apple M5 10코어(빠른 코어 4개 + 효율 코어 6개), RAM 24GB, Docker Desktop VM은 CPU 10개·9.7GiB
- 분할: 노트북에서 직접 돌렸다(`.venv`, 드라이버 8g)
- 적재·검사: Airflow 컨테이너 안에서 Spark local 모드로 돌렸다(드라이버 2g, ADR 0004)
- 측정 스크립트는 세 개다.
  - `bench/backfill.sh`: 백필 한 번을 돌리면서 3초마다 스케줄러 컨테이너의 메모리와 CPU 최대치를 기록하고, 결과를 `bench/results.csv`에 한 줄 남긴다.
  - `bench/spark_once.sh`: Spark 작업 하나를 Airflow 없이 같은 컨테이너·같은 드라이버 메모리로 돌린다. 시간과 최대 메모리를 재고, Spark 이벤트 로그를 남긴다.
  - `bench/stages.py`: 이벤트 로그에서 단계별 시간, 태스크 수, 코어 사용률, CPU 비율을 뽑는다.
- 같은 날짜를 다시 처리해도(`--reprocess-behavior completed`) 결과 데이터는 바뀌지 않는다(멱등). 그래서 같은 범위를 조건만 바꿔 여러 번 잴 수 있다.

## ② 동시 실행 수 (11월 30일치)
`spark` 풀 크기와 `--max-active-runs`를 K로 같이 바꿔 11월 30일치를 백필했다. 메모리·CPU는 스케줄러 컨테이너의 3초 간격 최대치다. K마다 한 번씩만 쟀다.

| K | 걸린 시간 | K=1 대비 | 성공/실패 run | 최대 메모리 | 최대 CPU |
|---|---|---|---|---|---|
| 1 | 906초 | 1.0배 | 30 / 0 | 3.2GiB | 977% |
| 2 | 528초 | 1.7배 | 30 / 0 | 5.8GiB | 805% |
| 3 | 401초 | 2.3배 | 30 / 0 | 7.5GiB | 954% |
| 4 (quality 재시도 없음) | 346초 | 2.6배 | 29 / **1** | 8.6GiB | 917% |

- 쉴 때 컨테이너 4개가 합쳐 약 1.1GiB를 쓴다(스케줄러 0.75, api-server 0.24, dag-processor 0.14, postgres 0.03). Docker VM은 9.7GiB다.
- K=1의 순수 태스크 시간은 load 418초 + quality 391초 + 도착 확인 4초 = 813초다. 나머지 93초(run당 약 3초)는 Airflow가 태스크를 잡아 넘기는 시간이다. 이 값은 `task_instance_history`에서 `state='success'`만 골라 뽑았다. 다시 처리하면 이전 시도가 이력 테이블로 옮겨지고, 대기 중인 새 시도는 옛 `start_date`를 단 채 `task_instance`에 남는다. 그래서 두 테이블을 그냥 합치면 중복으로 센다.

**K=4에서 메모리가 바닥났다.** 11/15 quality가 실패했다.
- Python 쪽 로그에는 `Answer from Java side is empty` → `Connection refused`만 남았다. Java 쪽 `OutOfMemoryError`는 없었다. JVM이 밖에서 죽었다는 뜻이다.
- Docker VM 커널 로그(`dmesg`)로 확인했다. postgres가 메모리를 요청한 순간 VM 전체가 모자랐다(`global_oom`). 커널은 가장 큰 프로세스인 Spark JVM을 죽였다(`Killed process (java)`, 실제 사용 `anon-rss` 2.2GiB).
- 드라이버 힙은 2g인데 실제 사용은 2.2GiB였다. 힙 밖에서도 메모리를 쓴다(클래스 정보, 스레드 스택, Parquet·zstd 버퍼). 그래서 메모리 예산은 힙 설정이 아니라 프로세스 실제 사용량(RSS)으로 잡는다. 계산하면 쉴 때 1.1GiB + 2.2GiB × 4 ≈ 10.1GiB로 VM(9.7GiB)을 넘고, K=3이면 7.8GiB로 들어간다.
- 11/15~17은 세일 기간이라 하루치가 평소(중간값 82MB)의 3.5배(275~293MB)다. 백필은 날짜 순서대로 도니, 큰 날 사흘이 같은 시간대에 겹친다. K는 평균 하루가 아니라 가장 무거운 날들이 겹치는 순간을 기준으로 정해야 한다.
- quality는 재시도가 없어서 run이 바로 실패했다. 실패 원인이 데이터만이 아니었으므로 quality도 재시도하게 고쳤다(ADR 0004 결정 4 정정).

**K=3까지 들어가고, 4부터 넘친다.** K=3의 최대 메모리 7.5GiB는 위 계산(7.8GiB)과 맞는다. K를 하나 늘릴 때 줄어드는 시간은 갈수록 작아진다.
- 1→2: 378초 줄었다(1.72배, 이상적이면 2배).
- 2→3: 127초 줄었다(1.32배, 이상적이면 1.5배).
- 3→4: 55초 줄었다(1.16배, 이상적이면 1.33배).
- 하루치 작업 하나가 코어를 1개만 쓰기 때문에 동시 실행이 효과가 있다(⑤ 병목 1). 효과가 줄어드는 것은 동시에 돌수록 태스크 하나하나가 느려지기 때문이다(⑤ 병목 3).

그래서 이렇게 정한다.
- **평소 풀은 2로 둔다.** 매일 도는 run은 하루에 하나라서 풀 크기와 상관이 없다. 2칸이면 메모리가 약 3.5GiB 남는다(K=2 최대치 5.8GiB + 다른 컨테이너 0.4GiB).
- **큰 백필은 3으로 돌린다(④).** 여유는 약 1.8GiB로 JVM 하나 분량이 안 된다. 한 번만 잰 값이고 3초 간격이라 순간 최대치를 놓쳤을 수 있다. 넘치더라도 재시도가 받아 주도록 quality 재시도를 먼저 고쳤다.
- K=6 스트레스 측정(계획에 있던 것)은 하지 않는다. K=4에서 이미 메모리가 넘쳤으니 K=6은 실패만 늘 것이 분명하다. 그러려고 Airflow 전체 상한(`parallelism`)까지 바꿀 이유가 없다.
- K=4는 다시 재지 않는다. OOM은 언제 날지 정해져 있지 않아서, 다시 돌려도 재시도 경로를 탄다는 보장이 없다. 대신 JVM을 직접 강제 종료하는 실패 훈련으로 재시도 회복을 확인했다(ADR 0004 '실패 훈련 2').

**측정 스크립트도 한 번 걸렸다.** K=3 다음 K=4 재측정이 시작하자마자 거절됐다.
- 마지막 run이 끝나고 25초 뒤에야 Airflow가 백필을 '끝남'으로 정리했다. 스크립트는 20초만 쉬고 새 백필을 만들려 했다(ADR 0004 알려진 한계).
- 스크립트가 풀을 4로 올린 채 죽어서, 평소 풀이 4로 남았다. 그대로 두었으면 다음 백필이 메모리를 넘쳤을 것이다.
- 이제 열린 백필이 닫힐 때까지 DB를 보며 기다린다. 중간에 죽어도 `trap`으로 풀을 2로 되돌린다.

## ③ 하루씩 vs 한 번에 (11월 적재만)
같은 컨테이너, 같은 드라이버 메모리(2g)로 비교했다. 한 번에 처리한 쪽은 `bench/spark_once.sh load_events --start 2019-11-01 --end 2019-11-30`이다.

| 방식 | 걸린 시간 | 비고 |
|---|---|---|
| 하루씩 30번 (K=1 백필의 load 태스크 시간 합) | 418초 | 태스크 사이 대기는 뺐다 |
| 하루씩 동시 3개 (K=3 백필 전체, 검사 포함) | 401초 | 참고용 |
| **한 번에 30일 (Spark 작업 1개)** | **90초** | 두 번 쟀다(앱 시간 94초·89초). 컨테이너 최대 메모리 3.4GiB |

한 번에 처리하는 쪽이 4.6배 빠르다. 이유는 두 가지다(⑤에서 확인).
1. 하루치는 gzip 파일 하나라서 단계마다 태스크가 1개뿐이다(코어 10개 중 1개). 한 달치는 파일 30개를 태스크 28~29개로 나눠 코어를 74~87% 쓴다.
2. 작업마다 드는 고정 비용(JVM·세션 시작, 실행 계획, 파일 나열, 결과 커밋, Airflow 태스크 준비)을 30번이 아니라 한 번만 낸다.

메모리는 날짜 수에 비례해 늘지 않았다(스케줄러 컨테이너 최대치로 하루치 2.0~3.2GiB, 한 달치 3.4GiB. 쉴 때 몫 0.75GiB를 포함한다). 힙이 2g로 묶여 있어서, 중복 제거 단계에서 힙에 들어가지 않는 데이터를 디스크로 내려 쓰기(spill) 때문이다. 한 달치는 메모리 기준 35.6GiB를 디스크에 7.0GiB로 내려 썼다(이벤트 로그의 `Memory/Disk Bytes Spilled`). 대신 시간이 든다.

**그래도 하루치 구조를 유지한다(배경의 사용자 결정).** 한 번에 처리하면 잃는 것이 있다.
- 다시 처리하는 단위가 한 달이 된다. 하루가 틀려도 30일을 다시 쓴다.
- 실패가 번지는 범위가 한 달이 된다. 적재는 깨진 행이 하나라도 있으면 바로 실패한다(`FAILFAST`). 그러면 어느 하루의 불량 행 하나가 30일 전체를 실패시킨다.
- 품질 검사와 알림이 날짜별로 나뉘지 않는다.
- 매일 운영할 때는 어차피 하루치만 도착한다. 한 번에 처리하는 이점은 대량 백필에서만 생긴다.

대량 백필만 월 단위로 적재하고 검사는 날짜별로 돌리는 길이 있다. `load_events`는 이미 날짜 범위를 받는다. 지금은 만들지 않는다. 7개월 전체 백필이 K=3으로 견딜 만한 시간 안에 끝나기 때문이다(④). 3단계에서 대량 재처리가 잦아지면 다시 본다.

## ④ 7개월 전체 처리량 (K=3)
`bench/backfill.sh 2019-10-01 2020-04-30 3`으로 돌렸다(2026-10-06 22:43~23:25).

| 항목 | 값 |
|---|---|
| 걸린 시간 | **2,516초 (41분 56초)**, 하루치 평균 11.8초 |
| run | 213개 모두 성공. 재시도 0회. 새 OOM 강제 종료 없음(`dmesg`) |
| 처리량 | 4억 1,033만 행(중복 제거 후) → 초당 약 16.3만 행. 압축 전 CSV 56.6GB(gzip 17.9GB) → 초당 22.5MB |
| 최대 메모리 | 8.1GiB. 다른 컨테이너 몫(0.4GiB)을 더하면 VM 9.7GiB에서 약 1.2GiB가 남는다 |
| 결과 | warehouse 날짜 폴더 213개, 7.2GB(zstd Parquet). landing gzip의 40%, 압축 전 CSV의 13%다 |

월별 결과다. run이 월 경계에서 겹치므로 처리 시간은 대략이다.

| 월 | 행(중복 제거 후) | 처리 시간 | load 평균 | quality 평균 |
|---|---|---|---|---|
| 2019-10 | 4,242만 | 337초 | 14.0초 | 14.3초 |
| 2019-11 | 6,740만 | 409초 | 18.1초 | 17.7초 |
| 2019-12 | 6,743만 | 413초 | 18.3초 | 16.9초 |
| 2020-01 | 5,583만 | 363초 | 15.3초 | 14.7초 |
| 2020-02 | 5,461만 | 353초 | 15.6초 | 15.8초 |
| 2020-03 | 5,618만 | 368초 | 15.9초 | 14.9초 |
| 2020-04 | 6,646만 | 389초 | 17.9초 | 16.4초 |

- 10월 행 수는 ADR 0004에 적은 값(42,418,544)과 같다. 다시 처리해도 결과가 같다(멱등).
- 처리 시간은 행 수만큼 늘지 않는다. 12월은 10월보다 행이 59% 많지만 시간은 23%만 더 걸렸다. 하루마다 드는 고정 비용(⑤ 병목 2)은 날짜 수에 비례하기 때문이다.
- ④의 11월(409초)은 ②의 K=3(401초)과 거의 같다. 측정이 재현된다.
- 최대 메모리는 11월만 돌릴 때(7.5GiB)보다 0.6GiB 높았다. 큰 날은 11월 세일 사흘(275~293MB)에 몰려 있고 12월 이후 가장 큰 날은 146MB라, 데이터가 커서 생긴 차이는 아니다. 원인은 확인하지 않았다. 측정 시간이 길어 3초 간격 측정이 더 높은 순간을 잡았을 수 있다. 어느 쪽이든 K=3의 여유는 JVM 하나 분량(2.2GiB)보다 얇다.

다른 방식으로 7개월을 돌린다면 이 정도 걸린다고 추정한다. 11월 비율로 계산했고 직접 재지는 않았다.
- K=1: 약 95분. K=2(평소 풀): 약 55분.
- 월 단위로 한 번에 적재(③의 방식, 검사 제외): 약 9분.

## ⑤ 병목
`bench/spark_once.sh`로 하루치 작업을 Airflow 없이 돌리고, `bench/stages.py`로 이벤트 로그를 나눠 봤다. 평범한 날은 11/05(82MB, 11월 중간값), 가장 큰 날은 11/16(293MB)이다.

| 작업 | 전체 | 단계 안(데이터 처리) | 단계 밖(드라이버 혼자) | 태스크 수 · 코어 사용 | CPU 비율 |
|---|---|---|---|---|---|
| load 11/05 | 10.5초 | 7.7초 | 2.1초 | 모든 단계 1개 · 10% | 94~98% |
| load 11/16 | 35.7초 | 32.9초 | 2.1초 | 모든 단계 1개 · 10% | 97~99% |
| quality 11/05 | 9.8초 | 6.5초 | 2.4초 | 가장 긴 단계(landing gzip 읽기 3.7초)가 1개 · 10% | 94% |
| 빈 작업(세션 시작 + 아주 작은 작업 + 종료), 3회 | 2.6~2.7초 | | | | |

- 코어 사용 = 태스크가 일한 시간 합 ÷ (단계 시간 × 코어 10개)
- CPU 비율 = 태스크가 CPU를 실제로 쓴 시간 ÷ 태스크 실행 시간

**병목 1. 하루치 작업은 코어 하나로 도는 계산이다.**
- landing은 날짜마다 `.csv.gz` 파일 하나다. gzip은 중간부터 풀 수 없어서 파일 하나를 태스크 하나가 처음부터 끝까지 읽는다.
- 셔플 뒤도 마찬가지다. `repartition("dt")`에 날짜가 하나뿐이라 모든 행이 한 파티션에 모인다.
- 그래서 적재의 모든 단계가 태스크 1개로 돈다. CPU 비율이 94~99%라 디스크를 기다리는 시간은 거의 없다. gzip 풀기, CSV 해석, 중복 제거, zstd 압축이 코어 하나를 꽉 채운다.
- 중복 제거는 하루치도 2g 힙에 다 들어가지 않아 디스크로 내려 쓴다(11/16: 메모리 기준 3.4GiB → 디스크 0.6GiB). 그래도 CPU 비율이 97%라 내려 쓰기가 병목은 아니다.
- ②에서 동시 실행이 효과가 있었던 이유가 이것이다. 하루치 하나가 코어 9개를 놀린다.
- 원천이 하루에 파일 하나를 떨군다는 가정(`split_raw`)이 이 병목을 만들었다. 실제 원천은 보통 시간 단위로 여러 파일을 떨군다.

**병목 2. 작은 날은 시간의 40%가 데이터와 상관없는 비용이다.** 11/05 run 하나(K=1에서 24.0초)를 나누면 다음과 같다.
- 데이터 처리(단계 안): 14.2초(59%)
- Spark 고정 비용(JVM·세션 시작, 실행 계획, 파일 나열, 커밋, 종료): 6.1초(25%). 작업마다 약 3초씩 load와 quality가 따로 낸다.
- Airflow 비용(태스크 준비, 태스크 사이 대기, 도착 확인): 3.8초(16%)
- 큰 날(11/16)은 load 35.7초 중 32.9초가 데이터 처리라 고정 비용이 묻힌다.
- 서로 다른 실행(Airflow K=1 측정, `spark_once.sh`)의 숫자를 합친 것이라 대략적인 값이다.

**병목 3. 동시에 돌리면 태스크 하나하나가 느려진다.** ② 측정의 태스크 기록이다.

| K | load 평균 | quality 평균 | 실효 동시 실행(Spark 태스크 시간 합 ÷ 전체 시간) |
|---|---|---|---|
| 1 | 13.9초 | 13.0초 | 0.89 |
| 2 | 16.3초 | 15.3초 | 1.80 |
| 3 | 18.3초 | 17.9초 | 2.71 |
| 4 | 20.8초 | 19.5초 | 3.44 |

- 실효 동시 실행이 K의 86~90%로 일정하다. Airflow 스케줄링 비용은 K와 상관없이 약 10%다.
- K가 늘수록 줄어드는 효과(②)는 태스크가 느려지는 데서 온다. K=4에서 load가 50% 느려졌다.
- 원인은 **가설**이다. 이 맥은 빠른 코어가 4개뿐이고 나머지 6개는 효율 코어다. 코어 하나를 꽉 쓰는 작업 K개가 JVM의 컴파일·GC 스레드, Airflow 프로세스와 빠른 코어 4개를 나눠 쓰다가 효율 코어로 밀린다고 본다. VM 안의 작업이 어느 코어에 배정됐는지는 macOS 밖에서 볼 수 없어서 확인하지 못했다.
- ②의 "최대 CPU 977%(K=1)"는 평균이 아니다. load는 처음부터 끝까지 코어 1개로 돈다. 반면 quality는 warehouse Parquet(나눠 읽을 수 있다)을 읽는 짧은 단계(0.3~0.5초)에서 태스크 10~11개로 코어를 90% 넘게 쓴다. 977%는 이런 짧은 순간의 최대치다. 최대치로 평균 사용률을 판단하면 안 된다.

**병목을 푸는 후보 (지금은 하지 않는다. 3단계 설계의 근거로 남긴다)**

| 후보 | 기대 효과 | 대가 |
|---|---|---|
| landing을 하루 여러 파일로 나누기(시간 단위 등) | 하루치도 여러 코어로 읽는다(병목 1) | `split_raw` 변경. 작은 파일이 늘어난다 |
| 대량 백필만 월 단위로 적재 | ③에서 4.6배 | 재처리 단위와 실패 범위가 커진다 |

| K 올리기 | K=3까지 | 메모리 상한(②). 빠른 코어가 4개뿐이다(병목 3) |

## 결론
1. **하루치 구조를 그대로 둔다.** 7개월(213일, 4.1억 행)을 노트북에서 42분 만에 다시 만들 수 있다(K=3). 재처리 비용을 감당할 만하므로, 날짜 단위로 다시 처리하고 검사하고 알리는 구조의 이점을 지킨다.
2. **동시 실행 상한은 메모리가 정한다.** K=3까지 들어가고(여유 약 1.2GiB), K=4는 메모리가 넘친다. 평소 풀은 2로 두고, 대량 백필 때만 3으로 올린다. 메모리 예산은 힙 설정(2g)이 아니라 프로세스 실제 사용량(2.2GiB)으로 잡는다.
3. **하루치 작업은 코어 1개로 도는 계산 병목이다.** 하루치가 gzip 파일 하나이기 때문이다. 같은 장비, 같은 엔진으로 한 달치를 한 번에 돌리면 4.6배 빠르다. 차이는 엔진이 아니라 구조에서 온다.
4. **측정하다가 결함 두 개를 찾아 고쳤고, 한계 하나를 기록했다.**
   - quality에 재시도가 없었다. 메모리 부족으로 JVM이 죽자 run이 바로 실패했다. → 재시도를 켜고 강제 종료 실험으로 회복을 확인했다(ADR 0004 결정 4 정정, 실패 훈련 2).
   - 측정 스크립트가 풀을 4로 남긴 채 죽었다. → 열린 백필을 기다리고 `trap`으로 풀을 되돌린다.
   - 재시도 대기가 누적 시도 번호로 계산되는 Airflow 동작은 고칠 수 없어 한계로 남겼다(ADR 0004 알려진 한계).
5. **3단계로 넘기는 근거**
   - landing을 하루 여러 파일로 나눌지 정한다(병목 1).
   - 대량 재처리용 월 단위 적재 경로가 필요한지 본다(③).
   - Spark를 Airflow 컨테이너 밖으로 뺄지 판단한다. 하루치 적재도 이미 디스크로 내려 쓴다(11/16: 0.6GiB). 셔플이 큰 세션화에서는 더 커질 것이다(ADR 0004 '다시 검토할 조건').

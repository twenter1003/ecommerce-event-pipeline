# 0007. 3단계 모델링: 세션화, 상품 SCD2, 퍼널·코호트 마트, lake DAG

- 날짜: 2026-10-07
- 단계: 3
- 상태: 채택 (2026-10-12, 3-3 완료)

## 배경
CLAUDE.md의 3단계 범위는 넷이다. Spark로 세션과 퍼널을 계산하고, fact/dim을 설계하고, 퍼널·전환율·코호트 마트를 만들고, 상품 속성 이력(SCD2)을 남긴다. 직접 나눈 세션은 원천의 `user_session`과 비교해 검증한다. 저장 계층은 ADR 0006이 정했다(SeaweedFS + Iceberg). 설계 과정은 ADR 0006 배경과 같다.

설계 전에 7개월 데이터를 탐색했다(2026-10-07, 노트북 PySpark). 결정의 근거가 된 사실은 다음과 같다.

## 결정 1. 테이블 5개 (모두 `lake.dw`)
| 테이블 | 한 행 | 파티션 | 쓰는 곳 | 쓰는 방법 |
|---|---|---|---|---|
| `fct_sessions` | 세션 | `dt` | `lake_daily` | 날짜 필터 덮어쓰기 |
| `product_daily` | (날짜, 상품) 속성 스냅숏 | `dt` | `lake_daily` | 날짜 필터 덮어쓰기 |
| `dim_product` | 상품 버전(SCD2) | 없음 | `lake_marts` | 차이만 MERGE |
| `mart_funnel_daily` | 날짜 | 없음 | `lake_marts` | 전체 덮어쓰기 |
| `mart_cohort_monthly` | (첫 방문 달, 활동 달) | 없음 | `lake_marts` | 전체 덮어쓰기 |

컬럼 정의(DDL)는 `pipeline/lake.py` 한 곳에만 둔다.

**계보 컬럼 `src_build`.** `fct_sessions`와 `product_daily`의 모든 행에 문자열 하나를 넣는다. 형식은 `<입력 파일 해시>-<실행 id>`다.
- 입력 파일 해시: `model_daily`가 읽기 직전에 본 events 날짜 폴더의 파일 이름 목록의 해시. Spark는 쓸 때마다 파일 이름에 새 UUID를 붙이므로, events를 다시 쓰면 이 값이 바뀐다.
- 실행 id: 실행마다 새로 만드는 uuid
- 날짜 안에서 값이 같아 사전 인코딩되므로 저장 비용은 거의 없다. 쓰는 곳은 결정 6의 신선도 관문이다.

**두 가지 원칙**
1. 날짜 단위 테이블(`fct_sessions`, `product_daily`)은 **그날 events만의 순수 함수**다. 그래서 처리 순서와 동시 실행을 신경 쓸 필요가 없고, `depends_on_past`도 필요 없다.
2. 날짜를 가로지르는 것(SCD2, 퍼널, 코호트)은 **날짜 단위 테이블 전체에서 매번 다시 계산**한다. 증분 상태를 들고 다니지 않는다.

**만들지 않는 것**
| 후보 | 이유 |
|---|---|
| `fct_event`(4.1억 행 + session_id 사본) | 7GB 넘게 다시 쓰는데 쓰는 곳이 없다. 이벤트가 어느 세션에 속하는지는 `(user_id, event_time BETWEEN session_start AND session_end)`로 되찾는다 |
| `dim_date` | 요일·월은 Spark 날짜 함수로 충분하다. 휴일·세일 달력 같은 원천이 없다 |
| `dim_user` | 속성이 첫 방문일 하나뿐이다. 코호트 쿼리 안의 한 줄이다 |
| 세션 검증 결과 테이블 | `fct_sessions`의 검증 컬럼 두 개로 같은 숫자를 계산한다(결정 2) |
| 카테고리별 마트 | SCD2가 쓰이는 곳은 as-of 검사와 Type-1/Type-2 비교 실험으로 충분하다 |

## 결정 2. 세션: 30분 비활동 + UTC 자정에서 끊는다
- 같은 사용자의 연속 이벤트 간격이 1,800초를 넘으면 새 세션이다. 정확히 1,800초는 같은 세션이다.
- 윈도는 `partitionBy(user_id, dt).orderBy(event_time, user_session, event_type, product_id, price)`다.
  - `dt`가 파티션 키라서 자정 절단이 자동으로 된다. 같은 함수가 하루치에도 여러 날 범위에도 맞고, 결과가 같다.
  - 정렬 키를 다섯 개로 둔다. 완전히 같은 행은 1단계에서 이미 지웠다. 그래서 이 다섯 키면 전체 순서가 하나로 정해지고, 다시 계산해도 결과가 같다.
- `session_id = "{user_id}-{세션 시작 epoch초}"`. 같은 사용자의 두 세션은 시작이 30분 넘게 떨어져 있어서, 해시 없이도 구조상 유일하다. 다시 돌려도 같은 값이고 사람이 읽을 수 있다.
- 세션마다 이벤트 수, 유형별 수, 구매 금액 합, 검증 컬럼 두 개를 저장한다.
  - `src_changed_at_start`: 우리 세션이 시작하는 이벤트에서 `user_session`도 바뀌었나. 그날 사용자의 첫 세션이면 NULL이다.
  - `src_changes_inside`: 우리 세션 안에서 `user_session`이 바뀐 횟수

**`user_session`과 비교하는 검증**
- 모집단은 같은 사용자·같은 날의 연속 이벤트 쌍이다.
- TP = `count(src_changed_at_start = true)`, FP = `count(… = false)`, FN = `sum(src_changes_inside)`
- 정밀도 = TP/(TP+FP), 재현율 = TP/(TP+FN).
- 기준값: 같은 정의(같은 사용자·같은 날의 연속 쌍, 자정에서 끊음)로 잰 11월 합산은 **정밀도 0.894, 재현율 0.399**다(3-2에서 잼).
  - 처음에는 "같은 정의로 0.960/0.688"이라고 적었다. 3-2 첫 실행에서 검사 2가 실패해 다시 쟀더니, 그 값은 사용자별로 한 달을 이어 센 값이었다. 같은 코드로 두 방식을 재면 사용자-월 0.961/0.688(FP 286,192, 배경 표와 같음), 사용자-일 0.894/0.399가 나온다.
  - 차이는 자정을 넘는 쌍 약 490만 개에서 온다. 하룻밤을 쉬었으니 양쪽 모두 거의 항상 나눈다. 그래서 TP로만 들어가 두 값을 부풀린다. 사용자-월 TP는 698만, 사용자-일 TP는 210만이다.
  - 정렬 키를 바꿔도(event_time만, user_session을 맨 뒤로), 비교 기준을 'user_session의 첫 이벤트'로 바꿔도 11/05 값은 ±0.001 안이다. 세션 수(10,964,869)는 탐색값과 같다.
- 재현율이 낮은 것은 버그가 아니라 정의 차이다. REES46은 짧은 간격에서도 세션을 나눈다. 30분은 업계 관행이라 골랐고, 일치율을 최대화하도록 맞추지 않는다. 마트는 우리 세션을 쓰고, `user_session`은 검증 기준으로만 쓴다.

| 기각한 후보 | 이유 |
|---|---|
| `user_session`을 그대로 세션으로 쓰기 | 정의를 모르는 블랙박스이고, 여러 사용자가 공유한 id도 있다. 세션화를 배울 수 없다 |
| 자정을 넘는 세션 허용 | D의 세션이 D−1의 꼬리와 D+1의 머리에 의존한다. 그러면 날짜 독립성이 깨진다. 대가 비교: 자정 절단으로 둘로 갈리는 세션은 0.25%다 |
| 10·60·120분 기준 | `--dry-run --gap-minutes`로 비교만 한다(3-2 표) |
| `row_number`, `monotonically_increasing_id` id | 다시 돌리면 값이 바뀐다 |

## 결정 3. 상품 SCD2: 원하는 상태를 매번 계산하고 차이만 MERGE한다
**버전 규칙**
| 속성 | 규칙 | 이유 |
|---|---|---|
| category_id, category_code | 둘을 한 쌍으로 null-safe 비교한다. null도 값('미분류')이다 | 하루 안에서 바뀌지 않는 속성이다. 12/1 재매핑과 2/1 개편이 버전이 된다 |
| brand | null은 '그날 관측 못 함'으로 보고 마지막 값을 이어 쓴다. null→값은 새 버전, 값→null은 변화 없음, 값→다른 값은 새 버전이다 | null과 값이 하루 안에 섞이는 경우가 37,921건이라, null은 빠진 데이터다. null→값을 첫 버전까지 거슬러 채우지 않는 이유는, 원천이 몰랐던 기간에도 브랜드를 알았던 것처럼 과거 결과가 거짓말을 하게 되기 때문이다 |
| price | SCD2에 넣지 않는다 | 상품마다 값이 많고(p99 71개) 하루 안에서도 바뀐다. 거래 시점의 측정값이라 events(사실)에 이미 있다 |

**계산 방법**
1. `product_daily`(그날 마지막 non-null brand, 그날의 카테고리)를 날짜별로 쌓는다.
2. 원하는 dim은 `product_daily` 전체의 순수 함수다(gaps & islands).
   - `product_id`별로 날짜순으로 보면서, 추적 속성이 앞 날과 다르면 새 버전을 시작한다.
   - `valid_from` = 그 버전의 첫 날, `valid_to` = 다음 버전의 첫 날(현재 버전은 `9999-12-31`), `is_current`
   - `product_sk = xxhash64(product_id, valid_from)`
   - 관측이 없는 날은 앞 버전이 덮는다.
3. 원하는 상태와 현재 dim을 `product_sk`로 full outer join한다. 다른 행만 골라 I/U/D 표시를 붙이고 `MERGE INTO` 한 번에 반영한다.
   - 모든 절에 표시 조건을 붙인다: `WHEN MATCHED AND op='D' THEN DELETE`, `WHEN MATCHED AND op='U' THEN UPDATE`, `WHEN NOT MATCHED AND op='I' THEN INSERT`.
   - 조건 없는 절을 두면 차이 계산에 버그가 있을 때 지울 행이 INSERT되는 식으로 조용히 반영된다. 조건을 붙이면 그런 행은 아무 일도 하지 않고, 검사 5가 불일치로 실패한다.
   - **차이가 0이면 MERGE를 하지 않는다.** 그래서 두 번째 실행은 커밋이 없다. 멱등성의 증거는 실행 전후 현재 스냅숏 id가 같다는 것이다.
   - 스냅숏 수로는 증명하지 않는다. 만료가 끼면 수가 바뀐다.
4. 원하는 상태는 `localCheckpoint()`로 한 번만 계산한다. 검사, 조인, MERGE가 같은 결과를 본다.

이렇게 하면 백필 순서가 섞여도, 지난 날짜를 다시 처리해도 dim이 같은 상태로 수렴한다. 매일 날짜순으로 처리하면 결과가 교과서식 SCD2 MERGE와 같다. 새 상품은 INSERT, 바뀐 상품은 옛 버전을 닫는 UPDATE와 새 버전 INSERT다.

**사실 테이블에 `product_sk`를 넣지 않는다.** 그 시점 버전은 as-of 조인(`e.dt >= valid_from AND e.dt < valid_to`)으로 붙인다. Kimball의 고전 방식은 적재할 때 sk를 찾아 사실에 박는다. 그러려면 dim이 날짜 순서대로 먼저 갱신돼 있어야 해서, 섞인 순서의 백필과 맞지 않는다.

| 기각한 후보 | 이유 |
|---|---|
| 날짜마다 증분 MERGE(어제 열린 버전과 오늘을 비교) | 세 가지가 깨진다. ① 순서가 섞이거나 지난 날을 다시 처리하면 이력이 깨진다. ② brand를 이어 쓰기 때문에 과거 하루가 바뀌면 그 뒤 모든 날이 연쇄로 바뀐다. ③ **read skew로 업데이트를 잃는다.** A(11/05)가 product_daily를 읽는다 → B(11/06)가 커밋한다 → A가 MERGE한다. A의 MERGE는 Iceberg 검증을 통과하지만, A가 계산한 상태에는 11/06이 빠져 있다. Iceberg 검증은 테이블 하나 안의 충돌만 본다 |
| 영향받은 상품만 날마다 다시 계산 | 순서와 무관하게 맞다. 하지만 하루에 영향받는 상품이 약 40%라 비용이 전체 재계산과 비슷하고, 213번 줄을 서야 한다 |
| `NOT MATCHED BY SOURCE DELETE`로 전체를 MERGE | copy-on-write가 매번 모든 파일을 다시 쓰고, 바뀐 게 없어도 스냅숏이 생긴다. 멱등성의 증거를 잃는다 |
| 전체 재계산 후 덮어쓰기 | 맞지만 변경 이력이 스냅숏에 남지 않고, MERGE를 배우지 못한다 |
| merge-on-read | delete 파일과 압축 관리가 늘어난다. 이 dim은 작고 읽기가 많다 |
| 속성 해시로 만든 sk | 값이 되돌아가면(acer→lenovo→acer) 서로 다른 두 버전이 같은 키가 된다 |

## 결정 4. 마트 두 개 (개수만 저장하고 비율은 조회할 때 계산)
**`mart_funnel_daily`**: 날짜마다 세션 단위 **존재 기준 퍼널**이다(그 유형의 이벤트가 세션 안에 있는가. 순서와 상품은 보지 않는다).
- 컬럼: sessions, s_view, s_view_cart, s_view_cart_purchase, s_purchase, s_purchase_no_cart, users, buyers, cart_events, purchase_events, revenue
- 달끼리 비교하는 기본 지표는 세션 전환율 `s_purchase / sessions`다. 장바구니를 거치지 않기 때문에, 10월의 장바구니 기록 누락에 흔들리지 않는다.
- 10월의 함정은 `cart_events / purchase_events`(10월 약 1.2, 다른 달 2.5~3.2)로 데이터 안에서 드러낸다.
- 비율을 저장하지 않는 이유: 날짜를 합칠 때 비율의 평균을 내는 실수를 부른다.

**`mart_cohort_monthly`**: 코호트는 첫 세션이 있었던 달(UTC)이다. 칸마다 active_users, buyers, cohort_users, months_since, is_left_censored를 둔다.
- 데이터가 정확히 달력 7개월이라 잘린 달이 없다. 칸 28개짜리 삼각형이다.
- 10월 코호트는 왼쪽이 잘려 있다(좌측 절단, 그 전부터 오던 고객이 섞임). 행은 남기고 `is_left_censored`로 표시한다. 비교는 11월 이후 코호트로 한다.
- 4월 코호트는 0개월 칸만 있다(우측 절단). 칸이 없다는 것은 0이라는 뜻이 아니다.

## 결정 5. Airflow: `events_daily`는 그대로, lake DAG를 따로 둔다
- **`events_daily`는 동작을 바꾸지 않는다.** GCP 스프린트에는 이 DAG만 Composer에 올린다. ADR 0004 결정 1의 약속("`spark_job()` 하나만 Dataproc 연산자로 바꾼다")이 그대로 지켜진다.
- **파일 배치:**
  - `spark_job()`, `alert_on_failure()`, `landed()`, 기본 재시도 설정을 `dags/common/airflow_utils.py`로 옮기고, `dags/.airflowignore`에 `common/`을 적는다.
  - lake DAG 두 개는 `dags/lake.py`에 둔다.
  - 스프린트에는 `events_daily.py`와 `common/`만 올린다.
  - DAG가 정의된 파일을 다른 파일에서 import하면, 그 DAG가 import한 파일에도 자동 등록돼 같은 dag_id를 두 파일이 주장한다(Airflow 3.3.1 `python_importer.py`). DAG가 없는 헬퍼 모듈은 import해도 그런 일이 없다.
  - lake 파일은 최상위에서 `pipeline`이나 Spark를 import하지 않는다. BashOperator로 `python -m`만 부르므로, lake 코드의 문제가 DAG 파싱을 깨지 않는다.
- **`lake_daily`**: 시간표는 events_daily와 같다(`CronDataIntervalTimetable`, UTC, end_date 2020-04-30). `wait_events → model` 순서다.
  - `wait_events` = `ExternalTaskSensor(events_daily.quality, allowed_states=["success"], failed_states=["failed", "upstream_failed"], mode="reschedule", timeout=6시간, retries=0)`
    - 센서는 run_id가 아니라 logical_date로 찾는다. 두 DAG의 시간표가 같으면 백필 run끼리도 날짜가 맞는다(providers-standard 1.17.0, 검증 확인).
    - `failed_states`가 없으면 events가 실패해도 기본 timeout 7일 동안 기다린다. 그동안 백필 자리를 차지한다.
    - 센서 실패는 알림 대상이 아니다. events의 실패는 events_daily의 quality 알림이 이미 알린다. 그래서 재시도를 0으로 둔다.
    - events를 고쳐 다시 처리한 뒤 lake_daily를 `--reprocess-behavior failed`로 다시 돌린다.
  - `model` = `python -m pipeline.model_daily --start {{ ds }}`(`spark` 풀). `spark_job()`이 붙이는 `--landing/--warehouse`를 받는다.
  - 이 DAG만 백필하면 lake를 다시 만들 수 있다. events는 건드리지 않는다.
- **`lake_marts`**: `schedule=None`, `max_active_runs=1`(trigger를 두 번 해도 차례로 돈다). 손으로 실행한다(`airflow dags trigger lake_marts`). 처리일을 쓰지 않으므로 trigger를 써도 된다.
  - **태스크 하나**(`python -m pipeline.marts`)다.
  - 순서: 입력 스냅숏 고정 → 신선도 관문 → dim 차이 MERGE → 퍼널 → 코호트 → 검사. 스냅숏 만료는 같은 프로세스의 `finally`에서 돈다.
  - 만료를 별도 태스크로 두면 run 상태가 마지막 태스크(만료)만 보고 정해진다. 그러면 관문이나 검사가 실패해도 run이 성공으로 보인다(Airflow 3.3.1 `dagrun.py`의 leaf 판정).
- `spark` 풀(2칸)을 events와 lake가 같이 쓴다. Airflow 전체의 JVM 수가 풀 하나로 묶인다. 센서는 기다리는 동안 칸을 잡지 않는다.
- `depends_on_past=False`를 유지한다. 날짜끼리 의존이 없다.
- **lake 백필의 동시 실행 수는 K=2가 기본이다.** K=3은 3-2에서 잰 값이 `1.1GiB(쉴 때) + seaweedfs + lake JVM 최대 RSS × 3 < 9.7GiB − 1.0GiB(안전 여유)`를 만족할 때만 쓴다. lake JVM은 Iceberg·AWS jar와 persist 때문에 2.2GiB보다 클 수 있다. `marts`의 메모리가 2.2GiB를 넘으면 `pool_slots`를 2로 줘서, 풀의 한 칸이 계속 JVM 하나 분량의 메모리를 뜻하게 한다.
- **운영 규칙:** events_daily를 다시 처리했으면 같은 범위의 lake_daily를 백필한다. 두 DAG의 백필을 동시에 열지 않는다. `bench/backfill.sh`가 두 DAG를 모두 보고 기다리게 해서 기계적으로 지킨다.

| 기각한 후보 | 이유 |
|---|---|
| `events_daily`에 `model` 태스크 붙이기 | 스프린트에서 213개 run이 모두 `model`에서 실패한다(compose에만 있는 Postgres·SeaweedFS·jar). lake만 다시 만들 때도 load·quality를 다시 돌리고, 원천인 events를 다시 쓰게 된다 |
| 파일 폴더만 보는 PythonSensor | 품질 검사를 통과했는지 모른다. 센서가 백필 처리일과 맞지 않을 때만 쓰는 대안(계획 B)으로 남긴다 |
| Asset 기반 스케줄 | 213개 이벤트가 몇 초 간격으로 들어올 때 run이 합쳐지는지 확인하지 못했다. Asset run에는 처리일도 없다 |
| 날짜 run마다 dim·마트 갱신 | 백필의 직렬 병목이 되고 read skew 위험이 있다(결정 3) |
| `depends_on_past=True` | 백필이 한 줄로 서고, 실패 하나가 뒤 날짜를 모두 막는다 |

## 결정 6. 품질: 쓰기 전에 검사하고, 마트 전에 신선도를 본다
**`model_daily`는 검사한 뒤에 쓴다.** 세션과 스냅숏 DataFrame을 `persist()`하고 아래 규칙을 먼저 계산한다. 모두 통과할 때만 두 테이블에 쓴다. 하나라도 실패하면 아무것도 쓰지 않고 실패한다(재시도 → 알림). 처음 설계는 '쓰고 나서 검사'였다. 반박 검증이 막아 냈다. 그대로 두면 검사에 실패한 날짜 데이터가 이미 커밋돼 마트로 흘러간다.

| # | 규칙 | 잡는 것 |
|---|---|---|
| 1 | 요청한 날짜마다 세션이 1개 이상이다(`set(dates) − 결과의 dt` = ∅) | 빈 입력 |
| 2 | 날짜마다 경계 정밀도 ≥ 0.50, 재현율 ≥ 0.05. **일치율을 채점하지 않고, 고장 난 세션만 막는 바닥이다.** 모두 한 세션으로 뭉치면 재현율이 0이고, 이벤트마다 나뉘면 정밀도가 0.05~0.08이다. 판단할 경계가 없으면(분모 0) 1로 본다. 3-2에서는 0.85/0.30(11월 최저에서 여유를 뺀 값)이었다. 3-3에서 213일을 재 보니 원천의 세션 정의가 기간마다 달라 61일이 걸려서 바꿨다('3-3 결과') | 세션이 뭉치거나 쪼개지는 고장(시각 정보 손실, 간격 단위 실수) |
| 3 | events에서 상품-날짜마다 (category_id, category_code) 조합이 하나다 | 스냅숏이 `max()`에 기대는 전제. 깨지면 `max`가 조용히 하나를 고른다 |
| 4 | 그날 events 행 수 = Σ 세션 이벤트 수 = Σ 유형별 수 | 단계 사이 행 수 대조. ADR 0004의 '입고 칸 고유 행 수 = 창고 행 수'의 3단계판이다. persist한 결과 위의 집계 하나라 비용이 거의 없다 |

표 안의 구조로 보장되는 성질은 운영 검사에서 빼고 호스트 테스트로 고정한다. id 유일, 자정 절단, 세션 사이 간격 > 1,800초 같은 것들이다. 단계 사이 대조(규칙 4)는 2단계에서 코드 밖의 결함 두 개를 잡았기 때문에 운영에 남긴다(ADR 0004).

**`lake_marts`의 신선도 관문 (쓰기 전에)**
1. 먼저 두 입력 테이블(`fct_sessions`, `product_daily`)의 현재 스냅숏 id를 읽어 고정한다. 관문과 이후의 모든 읽기는 그 스냅숏 기준이다. 검사한 시점과 고정한 시점 사이에 커밋이 끼는 틈을 없애려는 것이다.
2. events의 날짜 폴더마다, 고정한 스냅숏에서 `dt`별 `src_build`를 읽어 세 가지를 확인한다.
   - 두 테이블 모두에 그 날짜가 있고, 날짜 안에서 값이 하나다
   - 두 테이블의 값이 같다
   - 입력 파일 해시가 지금 events 폴더의 파일 이름 해시와 같다
3. 하나라도 어기면 쓰기 전에 실패하고, 다시 처리할 날짜 목록을 출력한다. 값이 없으면 낡은 것으로 본다.

이 관문이 막는 경로들:
- events를 다시 처리했는데 `lake_daily`를 다시 돌리지 않은 날짜
- `model`이 실패한 날짜
- 두 테이블 중 하나만 커밋되고 죽은 날짜(실행 id가 다르다)
- model이 읽은 뒤에 events가 다시 써진 날짜(읽기 직전에 기록한 파일 이름이 다르다)

대가: 내용이 같아도 events를 다시 썼으면 '낡음'으로 본다. 보수적이지만, 메시지대로 `lake_daily`를 다시 돌리면 풀린다.

**시각 비교를 버린 이유.** 처음 설계는 "lake 파티션의 `last_updated_at`이 events 파일 수정 시각보다 늦은가"였다. 2차 반박 검증이 두 가지를 찾았다.
- 만료가 값을 지운다. `.partitions`의 `last_updated_at`은 파일을 추가한 스냅숏이 살아 있을 때만 계산되고, 만료되면 NULL이 된다(Iceberg 1.12.0 `PartitionsTable.java`). 그러면 첫 `lake_marts`가 최근 10개만 남긴 뒤로는 약 203개 날짜에 값이 없다.
- 시계가 둘이다. events 파일 시각은 맥 호스트 파일시스템이 찍고, Iceberg 커밋 시각은 Docker VM의 JVM이 찍는다.

계보 비교는 시각을 쓰지 않으므로 둘 다 문제가 되지 않는다.

**`lake_marts` 안의 검사**: 원하는 dim 상태로 MERGE 전에 검사하고, MERGE 뒤에 한 번 대조한다.
| # | 규칙 |
|---|---|
| 1 | product_sk가 유일하다(xxhash64 충돌, MERGE 소스 중복 방지) |
| 2 | 상품마다 is_current가 정확히 1개이고, is_current ⇔ valid_to = 9999-12-31 |
| 3 | valid_from < valid_to이고, 붙어 있는 두 버전은 추적 속성이 다르다 |
| 4 | as-of 대조: product_daily의 모든 (dt, product_id)가 dim 버전 하나에 정확히 맞고, 카테고리가 같고, 스냅숏 brand가 null이 아니면 brand도 같다 |
| 5 | (MERGE 뒤) dim과 원하는 상태가 양방향으로 같다. 차이 MERGE 로직의 버그를 잡는다 |

## 다시 검토할 조건
- 하루 건수가 평소와 크게 다른 날(2020-02-27, 10%)을 막아야 하면 → 2단계 품질에 최근 7일 중앙값 대비 건수 규칙을 넣는다. 다른 날짜를 읽게 되므로 '날짜는 그날 데이터만의 순수 함수' 원칙의 예외로 ADR에 남긴다.
- 구매가 빠진 날(11/15, 1/2, 4/20·21)을 막아야 하면 → 2단계 품질에 이벤트 종류별 건수 규칙(예: 구매가 최근 7일 중앙값의 10% 미만이면 실패)을 넣는다. 위 건수 규칙과 같은 예외(다른 날짜 읽기)다.
- 정밀도나 재현율이 바닥 근처로 내려가는 날이 나오면 → 바닥을 바로 고치지 않는다. 원천 세션 길이 표로 원천 변화인지 우리 고장인지 먼저 가른다.
- 기간을 가로지르는 카테고리 분석이 필요하면 → 옛·새 category_id 대응표를 만든다. 같은 상품의 12/1 전후 버전 쌍에서 만들 수 있다.
- `lake_marts`가 운영에서 1분을 크게 넘으면 → 퍼널의 사용자 고유 수 두 개를 `(dt, user_id)` 집계 한 번으로 바꿔 Expand를 없앤다.
- 센서가 백필 처리일과 맞지 않으면 → 계획 B(events 날짜 폴더를 보는 PythonSensor)로 바꾼다. 이 경우 품질 관문은 신선도 관문과 `quality`의 실패 알림에 맡긴다.
- 마트를 매일 운영 시각에 맞춰 갱신해야 하면 → `lake_marts`에 시간표를 주거나 Asset 스케줄을 다시 본다.
- 이벤트 단위로 세션을 붙여 분석할 일이 생기면 → `fct_event`를 만든다.
- 사람이 정한 달력 속성(세일 기간, 휴일)이 필요해지면 → `dim_date`를 만든다.
- 하루 model 시간이 1분을 넘거나 읽기 단계가 전체의 절반을 넘으면 → 1단계 쓰기에 `parquet.block.size`를 줄여(예: 16MB) row group을 나누거나, `model_daily`가 읽은 뒤 `repartition`한다. 앞의 것은 events를 다시 써야 한다(3-2 셔플 표).

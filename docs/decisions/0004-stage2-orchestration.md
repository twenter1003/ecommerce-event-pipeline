# 0004. 2단계 자동화: Airflow 안에서 Spark 실행, 하루가 끝난 뒤 그 하루를 처리, 백필, 품질 검사와 알림

- 날짜: 2026-10-06
- 단계: 2
- 상태: 채택

## 배경
1단계 적재(`pipeline.load_events`)와 품질 검사(`pipeline.quality`)를 매일 자동으로 돌리고, 지난 날짜를 몰아서 처리(백필)하고, 실패하면 알려야 한다. ADR 0001은 이미 Airflow 3.3.1(Composer 3와 같은 버전), LocalExecutor, `parallelism=4`를 정했다. 결정 전에 조사 담당 4명이 사실을 따로 확인했다(2026-10-06). 각자 Airflow 3.3.1을 설치해 실제로 돌려 보거나, 설치된 소스를 읽거나, 해당 버전 문서를 봤다.

## 결정 1. Spark를 어디서 돌리나: Airflow 컨테이너 안에서 local 모드
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. Airflow 이미지에 Java 21과 PySpark를 넣고 BashOperator로 실행** | 추가 서비스가 없다. 1단계 명령을 그대로 쓴다. Spark JVM이 태스크 프로세스의 자식이라 같이 죽어서, "이전 시도가 아직 쓰는 중"인 상황이 생기기 어렵다 | Spark가 스케줄러 컨테이너와 메모리를 나눠 쓴다. 운영 환경과 모양이 다르다(운영에서는 연산을 밖으로 뺀다) |
| B. DockerOperator로 태스크마다 별도 컨테이너 | Airflow 이미지를 그대로 둔다. Kubernetes 위 운영 방식과 닮았다 | Docker 소켓을 열어 주면 root 권한과 같다. 마운트 경로를 호스트 기준으로 써야 한다. 스케줄러가 죽으면 남은 컨테이너가 계속 쓸 수 있다 |
| C. Spark 마스터·워커 컨테이너 + SparkSubmitOperator | 익숙한 패턴이다 | Python 앱은 standalone 클러스터에서 cluster 모드가 안 되어, 드라이버가 결국 Airflow 컨테이너에 남는다(Spark 4.1.2로 직접 확인). 컨테이너가 2개 늘고 메모리를 더 쓴다(하루치 2.0GB vs 1.2GB) |
| D. Spark Connect 서버 + 얇은 클라이언트 | Airflow 쪽이 가장 가볍다. 코드 변경 없이 동작했다 | 상시 서버가 하나 늘고, 그 서버가 죽으면 모든 태스크가 실패한다. 클라이언트와 서버 버전이 다르다 |

A를 고른다. 이 단계에서 배울 것은 DAG·백필·재시도·품질 검사다. 그래서 부품이 가장 적은 쪽에 시간을 쓴다. 클라우드 스프린트에서는 DAG의 `spark_job()` 함수 하나만 `DataprocSubmitJobOperator`로 바꾼다. 네 후보 모두 이 교체는 똑같이 필요해서, "운영과 닮았나"는 순위를 가르지 않았다.

이미지(`docker/airflow.Dockerfile`):
- Java 21: Debian bookworm 저장소에는 openjdk-21이 없다. 그래서 공식 Temurin 이미지에서 JRE만 복사하고 태그를 고정한다(`eclipse-temurin:21.0.12.1_1-jre`).
- PySpark 4.1.2: Airflow constraints와 함께 설치한다. `pip check`가 깨끗하다.
- **`apache-airflow-providers-apache-spark`는 넣지 않는다.** 이 provider가 끌고 오는 `pyspark-client 4.2.0`이 같은 `pyspark/` 폴더를 덮어쓴다. 그러면 `import pyspark`가 깨지는데, `pip check`는 정상이라고 나온다(조사에서 재현).
- 드라이버 메모리는 compose의 `PYSPARK_SUBMIT_ARGS=--driver-memory 2g`로 준다. 코드의 8g보다 우선한다(ADR 0003 한계 표의 마지막 줄 해결).
- Spark 태스크는 `spark` 풀(2칸)로 동시에 2개까지만 돈다. 실측 근거는 다음과 같다.
  - 2개가 동시에 돌 때 스케줄러 컨테이너가 최대 2.9GiB를 썼다(아래 측정).
  - Airflow 구성 요소는 쉴 때 합쳐 약 0.9GiB를 쓴다.
  - Docker VM은 9.7GiB다.
  - 몇 개까지 버티는지는 7개월 측정에서 잰다. → ADR 0005: 3개까지 들어가고 4개면 메모리가 넘친다. 평소 2칸은 그대로 둔다.

**ADR 0002 정정:** ADR 0002는 "pandas 3.0.5 때문에 Airflow와 Spark를 같은 환경에 둘 수 없다"고 적었다. 그런데 PySpark 4.1.2의 필수 의존성은 `py4j` 하나뿐이고, pandas는 선택 사항이다. 실제 충돌 원인은 pandas가 아니라 apache-spark provider였다. ADR 0002에 정정 메모를 남겼다.

## 결정 2. 처리일: 하루가 끝난 뒤 그 하루를 처리한다
Airflow 3.3에서 `schedule="@daily"`라고만 쓰면 기본 시간표가 `CronTriggerTimetable`이 된다. 설정 `create_cron_data_intervals`의 기본값이 False이기 때문이다. 이 시간표에서는 "10/1 run"이 10/1 0시, 즉 그날이 시작될 때 돈다. 그러면 아직 끝나지 않은 날을 처리하게 된다. 그래서 다음처럼 정한다.
- DAG에 `CronDataIntervalTimetable("@daily", timezone="UTC")`를 명시한다. 설정값과 무관하게 같은 동작을 보장한다.
- 처리일은 `{{ ds }}`로 받는다.
  - 정기 실행과 백필에서는 `data_interval_start`와 같다.
  - 수동 실행에서는 `data_interval_start`가 엉뚱한 날짜가 된다. CLI로 실행하면 "오늘의 전날", UI로 실행하면 "입력한 날짜의 전날"이다. 사용자가 입력한 날짜와 일치하는 것은 `ds`뿐이다.
  - 날짜 없이 수동 실행하면 `{{ ds }}`가 렌더링에 실패해서 태스크가 아무것도 쓰지 않는다.
- 주의: run 이름(`run_id`)은 처리일이 아니라 "실행된 시각"을 따른다. 10/1을 처리하는 run의 이름은 `backfill__2019-10-02T00:00:00`이다.

## 결정 3. 지난 날짜: 스케줄러가 몰아서 만들지 않고 백필로 돌린다
- `catchup=False`로 두고 `end_date`를 원본 마지막 날(2020-04-30)로 준다. 이미 지난 날짜라 일시정지를 풀어도 정기 run이 생기지 않는다.
- 지난 날짜는 `airflow backfill create --from-date … --to-date … --max-active-runs 2`로 돌린다.
- 백필은 스케줄러가 실행하고, DAG가 일시정지 상태면 진행되지 않는다. 그래서 compose에서 DAG가 일시정지 없이 시작하게 했다.
- 같은 날짜의 run은 DB 제약(`dag_id, logical_date` 유니크)으로 둘이 될 수 없다. 백필도 진행 중인 run은 건너뛴다. 그래서 ADR 0003 한계 2(같은 날짜 동시 쓰기)는 Airflow 안에서는 막힌다. Airflow 밖에서 손으로 적재를 돌리지 않는 것만 지키면 된다.
- 다시 처리할 때는 `--reprocess-behavior completed`를 쓴다. 새 run을 만들지 않고 기존 run을 다시 돌린다. 적재가 멱등이라 결과는 같다.

## 결정 4. 재시도와 기다림
| 태스크 | 설정 | 이유 |
|---|---|---|
| `wait_for_landing` | 1분마다 확인, 6시간 넘으면 실패, 기다리는 동안 실행 칸을 비움(`reschedule`) | "아직 안 왔다"와 "고장"을 구분한다. 늦게 오는 데이터로 실패 알림이 울리지 않게 한다 |
| `load` | 2회 재시도, 2분부터 두 배씩 늘려 최대 10분 | 메모리·디스크 같은 일시적 실패용이다. 적재가 멱등이라 다시 돌려도 안전하다 |
| `quality` | ~~재시도 없음~~ → load와 같이 2회 재시도 (아래 정정) | ~~같은 데이터로 다시 검사해도 결과는 같다. 바로 알린다~~ |

**정정 (2026-10-06, ADR 0005):** 처음에는 quality를 재시도 없이 두었다. "같은 데이터로 다시 검사해도 결과가 같다"는 이유였다. 그런데 이 이유는 실패 원인이 데이터일 때만 맞았다.
- 동시 실행 4개로 잰 백필에서 Docker VM 전체의 메모리가 바닥났다. 커널이 11/15 quality의 Spark JVM을 강제 종료했다(`dmesg`: `global_oom`, `Killed process (java)`, 실제 사용 2.2GiB).
- Python 쪽에는 `Answer from Java side is empty` → `Connection refused`만 남았다. Java 쪽 `OutOfMemoryError`는 없었다. JVM이 스스로 죽은 게 아니라 밖에서 죽었다는 뜻이다.
- 재시도가 없어서, 2분 뒤면 메모리가 풀려 통과했을 검사가 그대로 run 실패로 끝났다.

그래서 quality도 load와 같은 기본값(2회 재시도)을 쓴다. 데이터가 틀린 경우에는 재시도해도 또 실패하니, 알림이 늦어지고(처음 처리하는 날짜면 2분 + 4분, 아래 한계 참고) Spark를 두 번 더 돌린다. 하루 단위 배치에서는 받아들일 수 있다.

데이터 실패만 바로 알리는 방법도 있다. Airflow 3.3의 `retry_policy`(`ExceptionRetryPolicy`)는 예외 클래스를 보고 "바로 실패"와 "재시도"를 가른다. 다만 BashOperator는 종료 코드가 무엇이든 같은 예외를 던지므로 지금 구조로는 쓸 수 없다. 검사를 `@task`로 옮겨 "검사 규칙 실패"와 "Py4J 연결 끊김"이 서로 다른 예외로 드러나게 해야 한다. 알림 지연이 문제가 되면 그때 바꾼다.

## 결정 5. 실패 알림
- 태스크 단위 `on_failure_callback` 하나로 보낸다. 재시도를 다 쓴 뒤 한 번만 불린다.
- Slack 웹훅(`SlackWebhookNotifier`)을 쓴다. slack provider는 이미지에 기본으로 들어 있다.
- 연결(`AIRFLOW_CONN_SLACK_ALERT`)이 없으면 경고 로그 한 줄로 대신한다. 그래서 웹훅을 만들기 전에도 DAG가 깨지지 않는다.
- DAG 단위 콜백은 넣지 않는다. 실패 하나에 메시지가 두 번 가고, 실행 위치도 dag-processor로 갈라진다.
- 국내 팀 사례도 Slack이 표준에 가깝다(쏘카, 베이글코드 기술 블로그).

## 실행 환경
- `docker-compose.yml` 구성: postgres, 초기화(DB 준비와 `spark` 풀 생성), api-server, scheduler, dag-processor. triggerer는 기다림을 `reschedule` 방식으로 해서 필요 없다.
- 로그인은 끄고(`SIMPLE_AUTH_MANAGER_ALL_ADMINS`) 포트는 `127.0.0.1:8080`에만 연다. 로컬 전용이다.

## 측정 (2026-10-06, Docker Desktop VM 10코어·9.7GiB)
| 항목 | 값 |
|---|---|
| 10월 백필 | 31개 run이 모두 성공했다. run 하나(도착 확인 + 적재 + 품질 검사)는 평균 24초(19~27초) 걸렸다. 28일치를 동시 2개로 돌려 8분 |
| 메모리 | Spark 2개가 동시에 돌 때 스케줄러 컨테이너가 최대 2.9GiB를 썼다. 쉴 때는 Airflow 구성 요소를 합쳐 약 0.9GiB다 |
| 다시 처리한 뒤 warehouse | 42,418,544행, 날짜 폴더 31개, 폴더마다 파일 1개. 처리 전과 같다(멱등) |
| 1단계처럼 Spark 한 번에 31일 | 37초. 하루씩 31번 돌리면 그보다 훨씬 오래 걸린다. 이 차이는 하루마다 JVM을 새로 띄우고 검사를 따로 돌리는 비용이다. 7개월 측정에서 따로 잰다 |

**실패 훈련.** 원천이 이상한 데이터를 보낸 상황을 흉내 냈다.
1. 10/5 landing에 시각이 빈 행 1개짜리 파일을 더했다.
2. 그 상태로 10/5를 다시 처리했다.
   - 적재는 성공했다. 빈 시각 행이 날짜 필터에서 조용히 빠졌기 때문이다.
   - 품질 검사가 `warehouse 1,329,334 vs landing 고유 1,329,335`로 실패했다.
   - 콜백이 가짜 Slack 서버(노트북 127.0.0.1)로 `[실패] events_daily.quality 처리일=2019-10-05 시도=2`와 로그 링크를 보냈다.
3. 불량 파일을 지우고 `--reprocess-behavior failed`로 다시 처리했다. 10/5가 정상으로 돌아왔다.

이 훈련으로 ADR 0003이 2단계로 넘긴 "조용히 빠지는 행"이 실제로 검사에 걸리는 것을 확인했다.

**실패 훈련 2 (2026-10-06, 결정 4 정정을 확인).** 메모리 부족으로 JVM이 죽는 상황을 흉내 냈다. OOM은 언제 날지 정해져 있지 않아서, 같은 신호(SIGKILL)를 직접 보냈다.
1. 11/05를 다시 처리하고, quality의 Spark JVM이 뜨고 3초 뒤 `kill -9`로 죽였다(22:24:49).
2. 로그는 실제 OOM 때와 같았다(`Answer from Java side is empty` → `Connection refused`). 태스크는 `up_for_retry`가 됐고, 알림은 가지 않았다.
3. 22:34:50에 다시 시도해 8개 규칙을 모두 통과했고, run은 성공했다.

재시도까지 2분이 아니라 10분이 걸렸다. 아래 '알려진 한계'의 지수 대기 항목이 그 이유다.

## 알려진 한계
- 한 DAG에 진행 중인 백필은 하나뿐이다. 앞 백필이 Airflow 안에서 '끝남'으로 정리되기 전에 새로 만들면 만들어지지 않는다(실제로 겪음). 앞 백필이 끝난 것을 확인하고 넣는다.
- 재시도 대기는 "이번 run에서 몇 번째 실패인가"가 아니라 태스크의 누적 시도 번호로 계산된다(`2분 × 2^(시도 번호−1)`, Airflow 3.3.1 `TaskInstance.next_retry_datetime`). 백필로 다시 처리할 때마다 시도 번호가 올라가므로, 여러 번 다시 처리한 날짜는 첫 재시도부터 상한인 10분을 기다린다(실패 훈련 2). Airflow 소스 주석도 이 점을 인정한다. 상한(`max_retry_delay`)이 없었다면 1시간 넘게 기다렸을 것이다.
- 날짜를 다시 처리할 때 CLI `dags trigger`를 쓰지 않는다. 처리일 계산이 백필과 다르다(결정 2). 백필을 쓴다.
- Spark가 스케줄러 컨테이너 안에서 돈다. 메모리가 바닥나면 커널이 가장 큰 프로세스(JVM)를 먼저 죽이므로 보통은 태스크 실패로 끝난다. 그래도 위험을 줄이려고 풀 2칸, 드라이버 2g, 30분 상한을 둔다.
- 도착 확인은 로컬 경로를 찾아보는 방식(`glob`)이다. 스프린트에서는 GCS 센서로 바꾼다.
- Composer 3 이미지에 slack provider가 있는지, 바깥으로 나가는 네트워크가 열려 있는지는 확인하지 않았다. 웹훅을 넣은 뒤(로컬이든 Composer든) `airflow connections get slack_alert`로 읽히는지 보고, 실패 훈련을 실제 채널로 한 번 더 한다.

2026-10-06 코드 리뷰(관점 3개: DAG·Airflow 동작, 운영·보안, 품질 검사 정확성) 결과다. 리뷰어가 지적한 것을 다른 검증자가 재현했다. 고친 것은 다음과 같다.
- **품질 검사가 다른 적재와 부딪혀 잘못 실패할 수 있었다.** warehouse 루트를 읽으면 모든 날짜 폴더를 나열하고, 첫 폴더(10/1)의 파일로 스키마를 정한다. 그래서 10/1을 다시 적재하는 순간과 겹치면 "파일 없음"으로 실패했다(재현: 1,267회 중 212회). 이제 그 날짜 폴더만 직접 읽는다. 날짜마다 213개 폴더를 나열하던 비용도 없어졌다.
- **반올림을 잡는 규칙을 더했다(8번째).** 원래는 행 수 대조가 가격 반올림까지 잡는다고 적었지만 틀렸다. 반올림 때문에 행이 합쳐질 때만 잡힌다. 이제 반올림 전후 값을 비교한다. 자릿수를 세지 않고 값을 비교하는 이유는 `12.340`처럼 자릿수는 셋이지만 값이 그대로인 경우를 실패로 치지 않기 위해서다.
- **웹훅 설정 오류가 "아직 안 넣음"과 같은 경고 한 줄로 묻혔다.** JSON 오타나 URL만 넣은 경우도 "연결 없음"과 같은 예외가 난다. 이제 값이 있는데도 못 읽으면 error로 남긴다.
- **날짜 없이 수동 실행한 run이 실패하면 콜백이 KeyError로 죽어 알림이 가지 않았다.** `context.get("ds")`로 고쳤다.
- **Spark가 죽지 않고 멈추면 감지하지 못했다.** Spark 태스크에 30분 상한(`execution_timeout`)을 두었다. 메모리가 바닥났을 때 커널은 가장 큰 프로세스인 JVM을 먼저 죽인다. 그래서 스케줄러가 같이 죽기보다 태스크 실패로 드러나고, 남는 위험은 멈춤이었다.
- **스케줄러가 죽으면 다시 뜨지 않아 백필이 알림 없이 멈췄다.** 오래 도는 서비스에 `restart: on-failure`를 주었다.
- **토큰 서명 키가 저장소에 고정값으로 적혀 있었다.** 이제 `.env`에 넣지 않으면 compose가 뜨지 않는다.

남긴 것은 다음과 같다.
- 로그인이 꺼져 있다. 그래서 같은 Mac의 다른 프로세스나, DNS rebinding을 쓰는 악성 웹페이지는 관리자 API를 쓸 수 있다. 로컬 학습용이라 받아들인다. 이 compose를 VM에 그대로 올리지 않는다(ADR 0001 플랜 B). 올린다면 `SIMPLE_AUTH_MANAGER_ALL_ADMINS`를 끄고 SSH 터널로만 접속한다.
- 원천이 같은 날짜에 **이름이 다른** 정정 파일을 더하면, 옛 파일과 함께 읽혀 섞인 채 검사를 통과한다. 행 수 대조는 같은 합집합끼리 비교하므로 구조상 이것을 잡지 못한다. landing 계약은 "정정은 날짜 폴더를 통째로 교체한다"이다. 지금은 `split_raw`가 이 계약을 지킨다. 실제 원천을 붙이면 다시 본다.
- 가격의 표기만 다른 같은 값(`10.5`와 `10.50`)이 한 날짜에 함께 있으면, 행 수 대조가 잘못 실패한다. 데이터를 잃지 않는 거짓 경보라 받아들인다.
- 스프린트에서 Composer로 옮길 때는 `spark` 풀을 먼저 만든다. 풀이 없으면 태스크가 실패도 알림도 없이 영원히 대기한다.

## 다시 검토할 조건
- 3단계에서 셔플이 큰 작업 때문에 스케줄러 컨테이너 메모리가 모자라면 → Spark를 밖으로 뺀다(B 또는 D).
- 검사 결과를 기록으로 남기고 보고서로 보여 줘야 하면 → Great Expectations를 다시 검토한다.

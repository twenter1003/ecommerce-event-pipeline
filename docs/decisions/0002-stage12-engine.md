# 0002. 1·2단계 처리 엔진: PySpark vs DuckDB vs Polars

- 날짜: 2026-10-04
- 단계: 1~2 (3단계 이후에도 영향)
- 상태: 채택

## 배경
1단계(월별 CSV → 날짜 파티션 Parquet, 멱등 적재, 중복 제거) 코드를 짜기 전에 어떤 엔진 위에서 짤지 정해야 한다. 3단계는 Spark로 정해져 있고, ADR 0001의 GCP 스프린트는 "같은 DAG를 Composer에 올려 Dataproc에서 7개월 백필"을 전제로 한다. 데이터 규모(10월 5.67GB, 7개월 56.6GB)는 단일 노드 엔진으로 충분하다.

## 후보
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. PySpark** (1단계부터) | 스프린트에서 같은 코드를 Dataproc에 그대로 제출한다. 3단계에서 다시 짜지 않는다. DE 채용 공고 대부분에 나온다. | Java, 버전 고정 필요. 단일 노드에서는 JVM 부담으로 보통 가장 느리다. 1단계에서 개념과 Spark 실행 모델을 한꺼번에 배운다. Airflow 3.3.1 제약(pandas 3.0.5)과 한 환경에 두기 어렵다. 이 규모에 Spark는 과하다. |
| **B. DuckDB** → 3단계에 Spark | 설치가 패키지 하나다. 빠르다. 개념에만 집중한다. SQL이라 BigQuery로 옮기기 쉽다. | Dataproc에서 못 돌려 스프린트를 다시 설계해야 한다. 3단계에서 Spark를 새로 배우고 로직을 다시 짠다. |
| **C. Polars** → 3단계에 Spark | 설치가 패키지 하나다. 빠르다. API가 PySpark와 비슷해 3단계로 넘어가기 쉽다. | B와 같은 스프린트 문제와 재작성 비용이 있다. 채용 공고에 거의 나오지 않는다. |

## 결정
1단계부터 PySpark(로컬은 `local[*]`)로 적재·중복 제거·품질 검사 코드를 짜고, 같은 코드를 GCP 스프린트(Dataproc)와 3단계까지 이어 쓴다.

## 이유
- 얻는 것:
  - 코드 한 벌: 로컬에서 짠 적재 코드를 스프린트에서 Dataproc에 그대로 제출하고, 3단계에서 다시 짜지 않는다. 주 10시간에서 재작성 시간을 아낀다.
  - Spark를 쉬운 문제부터 배운다: 1단계(파티션 나누기·덮어쓰기)에서 실행 모델을 먼저 익히고, 3단계에서는 세션화·셔플 같은 어려운 부분에만 집중한다.
  - "적재 → 오케스트레이션 → 클라우드 백필 → 모델링"을 Spark 하나로 끝까지 해 본 경험이 남는다. B·C도 3단계에서 Spark를 쓰지만, 파이프라인 전체를 Spark로 운영해 본 경험은 A만 남긴다. 그래서 "취업에 도움"은 Spark를 써 봤다는 데서 나오지 않는다. 같은 코드를 로컬과 클라우드에서 모두 운영해 봤다는 데서 나온다.
- 포기하는 것:
  - 로컬 속도: 이 규모에서는 DuckDB·Polars보다 느리다.
  - 설치와 버전 관리 부담: Java와 버전 고정이 필요하다. Airflow와는 같은 환경에 둘 수 없어 컨테이너를 나눠야 한다.
  - 학습 부담: 1단계에서 데이터 개념(멱등성·파티셔닝)과 Spark 사용법을 동시에 배운다.
  - 원칙과의 충돌: "규모에 맞지 않는 기술을 억지로 넣지 않는다"는 원칙에 걸린다. 10월 한 달(5.67GB)만 보면 Spark는 과하다. 감수하는 근거는 둘이다. 하나는 7개월(56.6GB)치 Dataproc 백필과 3단계 Spark가 이미 정해져 있다는 점이다. 다른 하나는 로컬에서도 클러스터가 아니라 단일 노드(`local[*]`)로 돌려서 운영 비용을 최소로 둔다는 점이다.
- 면접 답변 요약("5GB에 왜 Spark?"): 이 규모만 보면 과한 게 맞다. 다만 같은 코드를 클라우드에서 7개월 백필하고 3단계 모델링까지 이어 가려고 1단계부터 Spark를 골랐다. 느려질 때의 기준은 '다시 검토할 조건'에 미리 정해 뒀다.

## 환경 (Claude가 정함, 2026-10-04 설치·확인)
- PySpark **4.1.2**로 고정한다(`pyproject.toml`). Dataproc 이미지 **3.0**의 Spark 4.1.2와 같은 버전이라, 스프린트에서 같은 코드가 그대로 돈다. pip 최신 4.2.0은 어느 Dataproc 이미지와도 맞지 않는다. Dataproc 2.2/2.3(Spark 3.5.3)은 체험 후 로컬에서 계속 쓸 버전으로 너무 오래됐다.
- Java는 **21**(Homebrew `openjdk@21`)이다. Dataproc 3.0, Kafka 4.3과 같다.
- 로컬 Python은 3.11(Composer와 같음)이고 Dataproc 3.0의 Python은 3.12다. 드라이버 코드는 두 버전에서 똑같이 돈다.
- pandas는 지금 넣지 않는다. PySpark에서 pandas는 선택 사항이다. Airflow와의 충돌(pandas 3.0.5 vs PySpark의 `<3`)은 2단계에서 Airflow와 Spark를 다른 컨테이너로 나눠 피한다.
- 확인: `local[*]`(10코어)에서 Spark 4.1.2, Java 21.0.12로 SparkSession 생성과 `range(1000).count()`가 성공했다.

## 다시 검토할 조건
- 10월 한 달 처리가 로컬에서 너무 느려 학습 흐름을 끊으면 → 어디서 시간이 걸리는지 Spark UI로 먼저 확인한다. 그래도 안 되면 1단계 탐색만 DuckDB로 하고 적재 코드는 Spark로 유지한다.
- 체험 계정에서 Dataproc 3.0을 만들 수 없으면 → 2.3으로 내리고 PySpark를 3.5.x로 고정한다.

## 정정 (2026-10-06, ADR 0004)
위 '포기하는 것'과 '환경'에 적은 "pandas 3.0.5와 PySpark가 충돌해 Airflow와 Spark를 다른 컨테이너로 나눠야 한다"는 내용은 틀렸다.
- PySpark 4.1.2의 필수 의존성은 `py4j` 하나뿐이다. pandas는 선택 사항이고 상한도 없다.
- 실제로 충돌하는 것은 `apache-airflow-providers-apache-spark`가 끌고 오는 `pyspark-client`다. 이것이 같은 `pyspark/` 폴더를 덮어쓴다.
- 그래서 2단계에서는 provider를 빼고, Airflow 이미지 안에 PySpark를 함께 넣었다. 자세한 내용은 ADR 0004 결정 1에 있다.

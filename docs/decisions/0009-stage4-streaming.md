# 0009. 4단계 실시간: Kafka 재생, Spark Structured Streaming, 워터마크와 처리 보장

- 날짜: 2026-10-12
- 단계: 4
- 상태: 채택 (2026-10-12, 4-1·4-2·4-3 완료)

## 배경
CLAUDE.md의 4단계 범위는 세 가지다.
- 이벤트 시각을 현재로 옮겨 Kafka로 재생한다.
- 실시간으로 집계한다.
- 늦거나 순서가 뒤바뀐 이벤트를 처리한다.

배울 개념은 토픽·파티션·컨슈머 그룹·오프셋, 이벤트 시간과 처리 시간, 워터마크, 처리 보장 수준이다.

전제가 되는 사실:
- 원천은 시간 순서가 완벽히 정렬돼 있다(CLAUDE.md, 10월 전수 확인). 그래서 늦게 오는 이벤트는 **재생기가 일부러 만든다.**
- warehouse(1단계)는 완전 중복을 지운 날짜 파티션이다. 재생의 원천으로 쓴다. 중복이 섞이면 실시간과 배치의 대조가 흐려진다.
- 로컬 Docker VM은 9.7GiB다. 스택이 쉴 때 약 1.9GiB를 쓴다(2026-10-12 측정).

## 결정 2. Kafka: 단일 브로커 KRaft, 토픽 하나
- 이미지는 `apache/kafka:4.3.1`(안정판 최신, 4.3.2·4.4.0은 RC)이다. 힙 512m, 브로커와 컨트롤러를 한 노드에 둔다. compose `stream` 프로필로 필요할 때만 띄운다. 호스트 포트는 열지 않는다.
- 토픽은 `events` 하나다. 파티션 6개, 복제 1, 키는 `user_id`다.
  - 키가 같으면 같은 파티션에 들어가 사용자별 순서가 지켜진다. 세션을 이어 붙이는 계산에 필요하다.
  - 파티션 6개면 같은 그룹의 컨슈머를 6개까지 늘려 볼 수 있다. Spark도 마이크로배치마다 태스크 6개로 읽는다.
- 보존은 바이트로 정한다: `retention.bytes` 256MB, `segment.bytes` 64MB. **`retention.bytes`는 토픽 전체가 아니라 파티션마다 적용된다**(ADR 0001 부록 C). 그래서 상한은 256MB × 6 = 1.5GB다. 지우는 단위는 세그먼트라, 세그먼트가 보존보다 작아야 실제로 지워진다.
- 토픽은 재생기가 없으면 만든다. 자동 생성(`auto.create.topics.enable`)은 끈다. 오타 난 토픽 이름이 조용히 새 토픽을 만들지 않게 하려는 것이다.

| 기각한 후보 | 이유 |
|---|---|
| 브로커 3대 | 복제와 ISR을 배울 수 있지만 메모리가 3배다. 4단계 개념 목록에 없다 |
| Schema Registry + Avro | 컨테이너가 하나 늘고, 스키마 진화는 4단계 범위 밖이다. JSON으로 보내고 소비 쪽에서 스키마를 고정한다 |
| Kafka Connect, ksqlDB | 재생과 집계를 직접 짜는 것이 이 단계의 학습이다 |

## 결정 3. 재생기: 시각을 현재로 옮기고, k배속으로, 일부러 흐트러뜨린다
- 원천: warehouse에서 날짜 하나의 시간 구간을 읽는다(pyarrow). 기본값은 2019-11-16(가장 큰 날)의 일부 구간이다.
- **시각 옮기기:** 모든 이벤트에 같은 Δ(= 재생 시작 시각 − 구간 시작 시각)를 더한다. 간격은 그대로라, 옮긴 시각으로 1분 윈도를 세면 배치로 같은 구간을 센 값과 정확히 같아야 한다. 이것이 결정 5의 대조 근거다.
- **k배속:** 보내는 시각만 1/k로 줄인다. 이벤트 시각은 줄이지 않는다. 기본값 60배속이면 이벤트 시간 1시간을 벽시계 1분에 보낸다. 이벤트 시간과 처리 시간이 다르다는 것을 숫자로 보인다.
- **흐트러뜨리기(시드 고정, 다시 돌리면 같다):**
  - 비율 p(기본 5%)는 워터마크보다 적게 늦춰 보낸다(0~8분). 순서가 뒤바뀌지만 집계에 들어가야 한다.
  - 비율 q(기본 0.5%)는 워터마크보다 많이 늦춰 보낸다(15~20분). 버려져야 한다.
  - 늦춘 이벤트는 이벤트 시각을 바꾸지 않고, 보내는 시점만 뒤로 민다.
- 메시지는 JSON이다. 옮긴 `event_time`과 원래 시각 `src_event_time`을 함께 싣는다. Kafka 레코드 시각(CreateTime)은 보낸 시각이라, 한 메시지 안에서 이벤트 시간과 처리 시간을 나란히 볼 수 있다.
- 재생 기록(매개변수, 보낸 수, 늦춘 수)을 JSON 파일로 남긴다. 대조에 쓴다.

## 결정 4. 실시간 집계: 1분 이벤트 시간 윈도의 퍼널, 워터마크 10분, Iceberg에 추가
- 계산: 1분 텀블링 윈도마다 유형별 이벤트 수(view·cart·purchase)와 매출을 센다. 3단계의 `mart_funnel_daily`를 분 단위로 실시간에 만드는 셈이다.
- 워터마크는 10분이다. 결정 3의 p(0~8분)는 들어가고 q(15~20분)는 버려지도록 둘 사이에 둔다.
- 출력은 append 모드로 lake의 Iceberg 테이블 `rt_funnel_minute`에 쓴다. append 모드는 워터마크가 윈도 끝을 지나야 그 윈도를 한 번 내보낸다. 그래서 한 윈도가 두 번 쓰이지 않는다.
- 체크포인트는 SeaweedFS가 아니라 로컬 파일시스템(컨테이너 볼륨)에 둔다. 체크포인트 로그는 rename에 기대는데, 오브젝트 스토리지의 rename은 원자적이지 않다(ADR 0008에서 겪은 것과 같은 문제).
- 실행: 같은 이미지로 compose 서비스 `stream`을 띄운다. Airflow 태스크로 돌리지 않는다. 끝나지 않는 잡은 배치 오케스트레이터의 일이 아니다.

## 결정 5. 처리 보장과 검증
- **정확히 한 번(이 테이블 한정):** 두 가지가 맞물린다.
  - Kafka 오프셋은 Spark 체크포인트에 있다. Spark는 컨슈머 그룹에 커밋하지 않는다("Kafka source doesn't commit any offset", Spark 4.1.2 Kafka 통합 문서).
  - Iceberg 스트리밍 쓰기는 커밋마다 쿼리 id와 배치 번호(`spark.sql.streaming.queryId`·`epochId`)를 스냅숏 요약에 남긴다. 커밋 전에 마지막으로 커밋한 배치 번호를 찾아(`findLastCommittedEpochId`), 이미 커밋한 배치는 건너뛴다.
  - 이 건너뛰기는 Iceberg 문서에는 없다. 1.12.0 jar의 `SparkWrite$BaseStreamingWrite` 클래스에서 로그 문구 "Skipping epoch {} for query {} as it was already committed"로 확인했다.
  - 그래서 중간에 죽고 다시 떠도 결과가 같아야 한다. 실험: 재생 도중 `SIGKILL` → 재시작 → 배치로 센 값과 윈도마다 같다.
- **대조:**
  1. q = 0(버릴 이벤트 없음)이면 윈도마다 실시간 값 = 배치로 같은 구간을 센 값.
  2. q > 0이면 Σ(배치 − 실시간) = Spark가 보고한 `numRowsDroppedByWatermark`의 합.
- 3단계와 같은 원칙이다. 결과를 파이프라인 밖의 독립 계산과 맞춘다.

## 결정 6. 컨슈머 그룹은 Kafka 도구로 따로 본다
- Spark는 오프셋을 그룹에 커밋하지 않는다. 그래서 그룹의 동작(파티션 나눠 갖기, 리밸런싱, 커밋한 오프셋, 지연)은 Kafka에 들어 있는 `kafka-console-consumer.sh`와 `kafka-consumer-groups.sh`로 보인다. 코드를 새로 짜지 않는다.

**겪은 것**
- `AdminClient(...)`를 변수에 담지 않고 바로 `create_topics`를 부르면, 결과를 받기 전에 클라이언트가 정리돼 `_DESTROY`(handle destroyed)로 실패한다. 변수로 붙잡아 두도록 고쳤다.
- confluent-kafka(librdkafka)의 기본 파티셔너는 CRC32다. 자바 클라이언트(murmur2)와 해시가 달라, 섞어 쓰면 같은 키가 다른 파티션에 간다. 재생기는 `murmur2_random`을 쓴다.
- Kafka 4.3의 `kafka-console-consumer.sh`는 `--property` 대신 `--formatter-property`를 쓰라고 안내문을 찍는다. 출력을 셀 때 이 한 줄이 섞인다.
- 첫 전송 때 "Coordinator load in progress" 재시도 경고가 한 번 났다. 멱등 전송(`enable.idempotence`)이 브로커에서 생산자 id를 받는 순간이고, 브로커가 막 떴을 때만 난다.

**설계를 고친 것 (결정 4·5를 실험으로 바로잡음)**
1. **늦은 이벤트를 거르는 워터마크는 한 배치 전의 값이다.**
   - 워터마크가 오른 바로 다음 배치에 온 늦은 이벤트는 아직 옛 워터마크로 걸러서 들어간다. 테스트 두 개로 확인했다(`…dropped_and_reported`, `…right_after_watermark_moves_is_still_kept`).
   - 공식 문서도 "임계값보다 늦은 데이터는 버려진다고 보장되지 않는다(may or may not get aggregated)"고 적는다.
   - 그래서 워터마크보다 늦은 이벤트는 일부만 버려진다. E1에서는 35%였다.
2. **Spark의 `numRowsDroppedByWatermark`는 버린 이벤트 수가 아니다.**
   - 상태 연산 앞의 부분 집계가 먼저 묶은 행 수다. 같은 윈도의 늦은 이벤트 3개가 사라져도 1로 센다(테스트로 확인).
   - E1에서는 1,295건이 버려졌는데 이 지표는 95였다. 결정 5의 대조 2("차이 = 이 지표의 합")는 틀린 기준이었다.
3. **그래서 대조 기준을 바꿨다.** 시드가 고정이라 재생 계획을 다시 세워, 어떤 이벤트를 얼마나 늦췄는지 알 수 있다. 윈도마다 다음 두 가지를 본다.
   - 0 ≤ 배치 − 실시간 ≤ 그 윈도에서 워터마크보다 늦게 보낸 이벤트 수
   - 그런 이벤트가 없는 윈도는 다섯 값이 모두 같다
   - 근거: 워터마크보다 덜 늦은 이벤트는 버려질 수 없다. 그 이벤트보다 먼저 보낸 메시지의 이벤트 시각은 '그 이벤트 시각 + 늦춘 길이'를 넘지 못한다.
   - 실시간이 배치보다 크면 중복이다.
4. **틱(하트비트)은 걸러 내지 않고 셀 때만 뺀다.** `filter`로 거르면 Spark가 그 필터를 워터마크 연산 아래로 내린다. 이벤트 시각을 쓰지 않는 조건이라서다. 그러면 틱이 워터마크를 밀지 못한다. 틱만 든 윈도는 집계 뒤에 거른다.
5. 실시간 테이블에 계보 컬럼 `topic`을 넣었다. 재생마다 시각을 '지금'으로 옮겨서, 몇 분 간격으로 한 실험끼리 윈도 시간대가 겹쳤다. 처음에는 이것을 모르고 대조해 배치 합계가 두 배로 나왔다. 검사가 위반 107개로 잡아냈다.

**겪은 것**
- 합계가 `DECIMAL(20,2)`로 넓어지는데, Iceberg 스트리밍 쓰기는 표의 `(18,2)`로 좁혀 주지 않는다(`cannot be promoted`). 집계에서 직접 맞췄다. 배치 쪽은 `lake.overwrite()`가 표 스키마로 맞춰 쓴다.
- 재생 기록에서 요약 개수(`late`)가 같은 이름의 인자(`late` 비율)를 덮어써서, 검사가 모든 이벤트를 늦춤으로 셌다. 개수를 `n_late`·`n_very_late`로 바꿨다.
- Iceberg는 출력 행이 없는 마이크로배치도 커밋한다(added-records 없음). 5초마다 스냅숏이 생기니, `lake_marts`의 만료가 이 테이블도 정리한다(`TABLES`에 들어 있다).
- `collect()`는 타임스탬프를 파이썬 쪽 지역 시간(KST)으로 바꾼다. 테스트는 세션 시간대(UTC)로 문자열을 뽑아 비교한다.

## 4-3 결과 (2026-10-12)
**만든 것:**

- `tests/test_stream_sessions.py` 2개. 호스트 테스트는 모두 57개가 통과한다.

**실험 S1 (같은 구간, p 5%(0~8분 늦춤), q 0, 워터마크 10분, 틱 45분)**
| 항목 | 결과 |
|---|---|
| 세션 | 배치 103,053 = 실시간 103,053. 시작·끝·이벤트 수가 모두 같은 세션도 103,053이다 |
| 이벤트 | 751,420 = 751,420 |
| 상태 | 세션 상태 행 최대 44,215, 상태 메모리 최대 36.1MiB다. 같은 구간의 1분 퍼널은 16행, 0.0MiB였다. 배치 처리 중앙값은 280ms와 266ms로 비슷하다 |

**배운 것**
- **이벤트 시간으로 세면 도착 순서가 뒤섞여도 배치와 같다.** 5%가 최대 8분 늦게 섞여 들어왔다. 그래도 워터마크(10분) 안이면, 세션 윈도가 늦은 이벤트로 두 세션을 잇는 일까지 해서 배치와 같은 세션을 만든다(테스트 `…bridges_two_sessions_into_one`).
- **Spark 세션 윈도의 경계는 포함이다.** 다음 이벤트가 '마지막 이벤트 + 간격'과 같은 시각이어도 같은 세션이다. 그래서 간격 30분이 3단계 규칙(1,800초까지 같은 세션)과 그대로 맞는다. 처음에는 경계를 빼는 줄 알고 1,801초를 줬다가, 1,801초 떨어진 이벤트까지 한 세션으로 묶였다. 테스트가 잡았다. 공식 문서("no input received within gap duration")만으로는 경계를 알 수 없다.
- **상태는 키 수에 비례한다.** 세션은 사용자마다 상태를 들고 있어, 같은 입력에서 1분 퍼널보다 상태 행이 약 2,800배다. 하루 전체를 실시간으로 돌리면 이 값이 메모리 요구량이 된다. 워터마크를 키우면 세션 상태는 더 오래 남는다.
- **틱의 여유는 워터마크 + 세션 간격보다 길어야 한다.** 세션은 '마지막 이벤트 + 30분'이 워터마크를 지나야 닫힌다. 그래서 틱을 45분으로 줬다. 1분 퍼널에서는 30분이었다.
  - 실험 S3(틱 30분): 실시간 세션이 88,278개로, 배치(103,053개)보다 14,775개 적었다. 실시간에만 있거나 값이 다른 세션은 0개였다. 빠진 것은 모두 닫히지 못하고 상태에 갇힌 마지막 세션들이다. 틱 30분에서 워터마크 10분을 빼면 20분이라, 세션 간격 30분보다 짧다.

# 0003. 1단계 적재: 일별 landing → 날짜 파티션 Parquet, 멱등 덮어쓰기, 완전 중복 제거

- 날짜: 2026-10-06
- 단계: 1 (2단계 DAG의 태스크 단위가 된다)
- 상태: 채택

## 배경
10월 원본은 gz 파일 하나(1.74GB, 4,245만 행)다. 2단계에서는 Airflow가 하루에 한 번, 그리고 백필로 과거 날짜를 하나씩 다시 돌린다. 그래서 1단계 적재는 아래 네 가지를 만족해야 한다.
- "날짜 하나"를 단위로 돌 수 있어야 한다.
- 같은 날짜를 다시 돌려도 결과가 같아야 한다(멱등).
- 완전히 똑같은 중복 행을 지워야 한다.
- ADR 0002대로 같은 코드가 Dataproc(`gs://`)에서도 돌아야 한다.

원본 전수 확인(awk, 2026-10-06):
- 행 수와 형식: 42,448,764행. 시각 형식이 어긋난 행은 0개이고 모두 10/1~10/31 UTC 범위다.
- 가격: 소수 둘째 자리를 넘는 값이 0개이고 최대 2574.07이다.
- 빈 값: user_session 2행, brand 611만 행, category_code 1,352만 행.

## 결정 1. 원천 형태: 월 파일을 일별 landing 파일로 한 번 나눈다
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. 일별 landing으로 1회 분할** (`split_raw`) | 하루치 적재가 하루치 파일만 읽는다. 실제 원천이 매일 파일을 떨구는 모습과 같다. | 디스크를 한 벌 더 쓴다. 분할 단계 하나가 늘어난다. |
| B. 매번 월 파일 전체를 읽고 날짜로 거른다 | 단계가 하나 줄어든다. | gzip은 쪼갤 수 없어 태스크 하나가 1.7GB를 매번 푼다. 31일 백필이면 31번 반복한다. |
| C. 월 파일을 한 번에 적재하고 날짜 단위 재실행은 포기한다 | 가장 단순하다. | 2단계의 일 단위 DAG·백필과 맞지 않는다. |

landing에는 원본 값을 **문자열 그대로, 중복도 지우지 않고** 둔다. 정제는 적재 단계만 맡아야, 적재 규칙을 바꿨을 때 landing에서 다시 돌릴 수 있다. Spark CSV 쓰기는 기본으로 값 앞뒤 공백을 지우므로 이 기능을 끈다(리뷰에서 발견).

분할도 dynamic overwrite를 쓴다. 그래서 다른 달 행이 섞인 파일을 나누면, 먼저 나눠 둔 그 날짜 landing이 섞인 몇 행으로 통째로 덮어써진다. 이를 막으려고 **한 파일에 달이 둘 이상이면 실패**시킨다. 10월 파일은 10월 행만 있다. 11월 이후 파일은 아직 확인하지 않았다. 이 검사 때문에 gz를 한 번 더 읽지만, 1회성 단계라 감수한다(+15초).

## 결정 2. 파티션 기준: UTC 날짜 `dt`
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. UTC** | 원문이 UTC라 변환이 없다. 실행하는 기계의 시간대와 무관하다. | 한국 기준 "하루"와 9시간 어긋난다. |
| B. KST | 국내 서비스 지표와 날짜가 맞는다. | 원본 날짜 경계와 어긋나, 원본 하루치가 두 파티션에 걸친다. 이 데이터는 한국 서비스 로그도 아니다. |

세션 시간대를 `UTC`로 고정한다(`pipeline/spark.py`). 이 설정이 빠지면 dt는 맞게 나오지만 저장된 절대 시각이 9시간 밀린다. 읽기와 날짜 계산이 같은 시간대를 쓰기 때문이다. 그래서 테스트는 dt가 아니라 epoch 초로 확인한다.

## 결정 3. 멱등 적재: 요청한 날짜 파티션만 갈아 끼운다 (dynamic partition overwrite)
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. dynamic partition overwrite** | 데이터에 있는 날짜 파티션만 통째로 교체한다. 하루든 31일이든 같은 코드다. SQL의 `INSERT OVERWRITE ... PARTITION`과 같은 개념이다. | 행이 없는 날짜는 건드리지 않는다(아래 보완). 교체가 원자적이지 않다('알려진 한계'). |
| B. append 후 읽을 때 중복 제거 | 쓰기가 단순하다. | 재실행할 때마다 데이터가 불어난다. 읽는 쪽마다 중복 제거 책임이 생긴다. |
| C. 날짜 경로에 직접 static overwrite | 이해하기 쉽다. | 날짜마다 따로 써야 해서 여러 날짜를 한 번에 못 쓴다. |
| D. Delta Lake/Iceberg의 `replaceWhere`·MERGE | 교체가 원자적이고 이력이 남는다. | 이 규모·단계에 테이블 포맷을 추가로 배워야 한다. |

**보완: 요청한 날짜 중 행이 없는 날이 있으면 쓰기 전에 실패한다.** dynamic overwrite는 "데이터가 있는 파티션만" 교체한다. 그래서 원천이 어떤 날짜를 빈 파일로 정정해 보내면, 그 날짜의 옛 데이터가 그대로 남은 채 작업이 성공으로 끝났다(리뷰 3명이 각자 재현). 재실행할 때마다 결과가 같다는 뜻의 멱등성은 지켜지지만, "warehouse는 landing의 함수"라는 계약이 깨진다. 막는 비용은 `event_time`만 읽는 스캔 한 번이다(31일 적재 32초 → 37초). 역순 날짜 범위(`--start` > `--end`)도 같은 이유로 막는다.

## 결정 4. 중복 제거: 같은 날짜 안에서 9개 컬럼 전체가 같은 행만 하나 남긴다
- 문제 정의가 "완전히 똑같은 행"이다. 그래서 키를 고르지 않고 모든 컬럼을 비교한다(`dropDuplicates()`). 같은 사용자가 같은 초에 같은 상품을 두 번 본 것처럼 일부 컬럼만 같은 행은 실제 행동일 수 있어 지우지 않는다.
- 완전 중복은 `event_time`까지 같아서 늘 같은 날짜에 모인다. 그래서 날짜 단위 중복 제거만으로 테이블 전체에 중복이 없다.
- `repartition("dt")` 뒤에 `dropDuplicates()`를 하면 셔플이 한 번만 일어나고 날짜당 파일이 하나 나온다. 실행 계획으로 확인했다: Exchange는 `hashpartitioning(dt)` 하나뿐이고, 중복 제거(HashAggregate)는 그 분할을 그대로 쓴다. 날짜 필터는 옵티마이저가 `event_time` 범위 조건으로 바꿔 파일 스캔까지 내려보낸다.

## 결정 5. 형식이 깨진 행: FAILFAST + 헤더 대조
| 후보 | 장점 | 단점 |
|---|---|---|
| **A. FAILFAST** | 깨진 행이 하나라도 있으면 그 날짜 적재가 실패한다. 조용히 null이 되지 않는다. | 행 하나 때문에 하루치가 막힌다. |
| B. PERMISSIVE (기본값) | 멈추지 않는다. | 깨진 값이 null로 바뀌어 품질 검사 전까지 아무도 모른다. |
| C. DROPMALFORMED | 멈추지 않는다. | 몇 행이 버려졌는지 남지 않는다. |

10월 원본에는 깨진 행이 없다. 깨진 행을 따로 모아 두는 격리는 2단계 품질 검사에서 다룬다.

FAILFAST가 **잡는 것**: 시각 형식(UTC 없음·ISO `T`·소수 초), 숫자 아님, 가격 자릿수 넘침, 컬럼 수. **못 잡는 것** 둘은 2단계로 넘긴다(리뷰에서 재현).
- 빈 `event_time`: null이 되고 날짜 필터에서 조용히 빠진다.
- 소수 셋째 자리 가격: `12.345`가 `12.35`로 반올림된다. 그러면 원래 다른 두 행이 같아져 중복으로 지워질 수 있다.

헤더는 `enforceSchema=false`로 SCHEMA와 대조한다. 기본값(true)은 헤더를 건너뛰고 위치로만 읽는다. 그래서 컬럼 순서가 바뀐 파일(예: user_id↔product_id)이 타입만 같으면 값이 뒤바뀐 채 적재된다(리뷰에서 재현). 11월 이후 파일은 Kaggle이 아니라 data.rees46.com에서 받으므로 이 대조를 해 둔다.

## 결정 6. 저장
- zstd Parquet로 저장하고 날짜당 파일 하나를 둔다. 크기 비교는 아래 '측정'에 있다.
- 타입:
  - `price`는 `DECIMAL(10,2)`다. 원본에 소수 셋째 자리가 없어서 반올림으로 값이 바뀌는 일이 없다.
  - `category_id`는 int 범위를 넘어서 `BIGINT`다. 다른 ID도 같이 `BIGINT`로 맞춘다.

## 측정 (2026-10-06, 로컬 10코어 `local[*]`, 드라이버 8GB)
| 항목 | 값 |
|---|---|
| 분할 `split_raw` (1회성) | 100초(달 섞임 검사 전 85초). gz를 읽는 태스크 1개가 대부분을 차지한다. landing 31개 파일, 1,743MB |
| 31일 적재 `load_events` | 37초(빈 날짜 검사 전 32초) |
| 하루 재적재 (10/15) | 9초. 파일 수 1개 그대로, 건수 같음, 다른 날짜 폴더는 바뀌지 않음 |
| warehouse | 31개 파티션, 파일 31개, 734MB(zstd). ADR 0001의 사전 추정치 0.73GB와 맞는다 |
| 원본 행 = landing 행 | 42,448,764 = 42,448,764 (awk vs Spark) |
| 원본 내용 = landing 내용 | 줄을 정렬한 뒤 md5가 같다(`fdd819e2…`). 분할이 값·공백·따옴표·빈 값을 하나도 바꾸지 않았다 |
| warehouse 행 = 원본의 고유 행 | 42,418,544 = 42,418,544 (Spark vs `sort -u`) → 완전 중복 30,220행(0.07%) 제거 |

같은 결과를 서로 다른 도구 두 개로 맞춰 봤다(reconciliation). `sort -u`는 원문 텍스트를, Spark는 타입을 입힌 값을 비교한다. 그래서 두 수가 같다는 것은 타입 변환 때문에 행이 합쳐지거나 갈라진 일이 없다는 뜻이기도 하다.

## 알려진 한계
2026-10-06 코드 리뷰(관점 3개: Spark 동작, 이식성, 테스트 빈틈) 결과다. 리뷰어가 지적한 것을 다른 검증자가 작은 실험으로 다시 재현했다. 바로 고친 것은 위 결정에 반영했고, 아래는 남긴 것이다.

| 한계 | 언제 드러나나 | 어디서 막나 |
|---|---|---|
| 파티션 교체가 원자적이지 않다. Spark는 커밋할 때 날짜 폴더를 지운 뒤 staging 폴더를 옮긴다(`HadoopMapReduceCommitProtocol`). 그 사이에 죽으면 그 날짜가 비거나 일부만 남는다 | 커밋 중 드라이버가 죽을 때. GCS는 폴더 이동이 객체별 복사·삭제라 이 시간이 길다 | 같은 날짜를 다시 돌리면 복구된다. 2단계는 재시도에 맡기고, 품질 검사는 적재 태스크가 성공한 뒤에만 돈다. 스프린트에서는 계층형 네임스페이스(HNS) 버킷으로 폴더 이동을 원자적으로 만드는 방안을 검토한다 |
| 같은 날짜에 쓰는 작업 둘이 동시에 커밋하면 `dt=D/dt=D`처럼 폴더가 겹친다. 그러면 테이블 전체를 못 읽는다 | 수동 범위 백필이 일 단위 DAG와 같은 날짜를 동시에 쓸 때, 또는 재시도가 아직 커밋 중인 이전 시도와 겹칠 때 | 2단계 DAG에서 날짜당 쓰는 작업을 하나로 제한한다. 다른 날짜끼리 병렬로 쓰는 것은 안전하다(리뷰에서 6개 동시 실행을 3회 반복해 확인) |
| 빈 `event_time`이 조용히 빠지고, 소수 셋째 자리 가격이 반올림된다 | 이후 달 원본이 10월과 다를 때 | 2단계 품질 검사(ADR 0004). 행이 빠지는 것은 "landing 고유 행 수 = warehouse 행 수"가 잡는다. 반올림은 행이 합쳐질 때만 이 대조에 걸린다. 그래서 반올림 전후 값을 비교하는 규칙을 따로 두었다(2단계 리뷰에서 처음 주장이 틀렸음을 확인하고 고침) |
| dynamic 모드는 warehouse 루트에 `_SUCCESS` 파일을 남기지 않는다 | 2단계에서 `_SUCCESS` 센서를 쓰려 할 때 | 다음 태스크는 경로가 아니라 적재 태스크의 성공에 의존하게 한다 |
| `spark.driver.memory`를 코드에서 정해도 `python -m`으로 띄울 때만 적용된다 | 2단계에서 spark-submit으로 띄우면 조용히 1GB가 된다 | 띄우는 쪽에서 `--driver-memory`로 준다 |

## 다시 검토할 조건
- 원천이 같은 날짜 파일을 정정해서 다시 보내는 일이 잦아지면 → 원자적 교체가 필요하다(Delta/Iceberg 또는 staging 후 교체).
- 깨진 행 때문에 날짜 적재가 자주 멈추면 → 2단계에서 격리 경로를 둔다.
- 분석 쿼리가 시간 범위나 사용자로 자주 거르면 → 파일 안 정렬(`sortWithinPartitions`)을 검토한다.
